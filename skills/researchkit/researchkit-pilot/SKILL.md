# researchkit-pilot スキル（R6: 予備調査で問いを確かめる）

問いの立て方の誤りは、収集を始めてから見つかると高くつく。データが存在しない、検索語が当たらない、定義が合わない、相手が答えられない、といった問題を、**いちばん安い方法で、判定の基準を先に決めてから**確かめる。

ここで確かめるのは、**問いに答えられるかどうか**である。仮説が正しいかどうかではない。予備調査で見えた値を、仮説の支持・棄却の根拠にしない。また、見えた値に合わせて仮説を書き換えない（結果を見てから仮説を立てる HARKing〈Norbert L. Kerr, 1998〉を避けるため）。仮説を直してよいのは、答えられる形にするため（範囲を絞る、代わりの指標にする、定義をそろえる）だけである。

パスは `.researchkit/config.yaml` の `paths` で読み替える（既定は `docs/study/`）。進捗の記録とモードは [`researchkit-bootstrap`](../researchkit-bootstrap/SKILL.md) の §3・§7 に従う。

## 1. 引数

```text
$ARGUMENTS
```

- `H<n>` を並べると、その仮説だけを確かめる。省略すると、`hypotheses.md` の「答えられるか（R6）」が `未確認` か `保留` のすべてを対象にする。探索の葉（仮説なし）も、答えたと言える条件が判定できるかを同じ手順で確かめる。
- `--skip <理由>` を付けると、予備調査を行わずに省く（§5）。

## 2. 入力

- `docs/study/hypotheses.md`（仮説、反証条件、検証に要る証拠、確かめ方の見込み）
- `docs/study/issue-tree.md`（葉の問いと答えの形）
- `docs/scan/wide.md`（データの所在、検索の記録、仮の出典）
- `docs/concept/premises.md`（RP4 期限、RP5 予算、RP6 使えるデータとアクセス、RP9 倫理と個人情報）

`hypotheses.md` に反証条件のない仮説があれば、その仮説は書き直してから計画する（書き直しは `researchkit-hypothesis` の規則に従う。短い修正ならこのスキルで直し、`hypotheses.md` の「変更の記録」に書く）。

### 始める前に（検索の予算）

`$RK budget --step R6` を実行する（確かめる仮説が 1〜2 個だけのときは `--need <見積もり>`）。`VERDICT: STOP` なら始めずに止まり、新しいセッションで実行するよう案内する（steering「セッションの区切り」）。

## 3. 手順

### ステップ 1: 計画

[templates/plan.md](templates/plan.md) の様式で `docs/study/pilot/plan.md` を書く。仮説ごとに次を決める。

1. **確かめること**: 次の 3 つのうち、その仮説で危ういものを選ぶ。
   - **答えられるか**: 反証条件を判定できる証拠の形（数値の粒度、期間、定義、比較の対象）が、存在する証拠と合っているか
   - **手に入るか**: 証拠が、期限・予算・アクセス（RP4〜RP6）の範囲で手に入るか
   - **検索語は当たるか**: 検索式で、関係のある資料が適度な件数で見つかるか（多すぎず、少なすぎず、上位に関係のある資料が並ぶか）
2. **方法**: 下の表から、確かめることを判定できるうちで最も安いものを選ぶ。

   | 方法 | 向いていること | 実行 |
   |---|---|---|
   | 試しの検索 | 検索語は当たるか、文献があるか | AI が検索式を 2〜4 通り試し、件数と上位 10〜20 件の関係の有無を数える |
   | データの所在と中身の確認 | 答えられるか、手に入るか | AI が提供元のページを開き、項目、粒度、期間、定義、形式、ライセンスを確かめる。小さな表は試しに取得する |
   | 試しの集計 | 答えられるか（定義をそろえて計算できるか） | AI が小さな標本で、反証条件に使う値を 1 回計算してみる（スクリプトは `docs/study/pilot/scripts/`） |
   | 文献の入手の確認 | 手に入るか | AI が主な文献のオープンアクセスの版（著者の版、リポジトリ）の有無を確かめる。なければ `[人]` の入手の候補にする |
   | 質問票・ガイドの通読 | 答えられるか（相手が答えられる問いか） | AI が質問の案を書き、誘導、二重の問い、専門用語、答えにくさを点検する |
   | 試しの質問 | 答えられるか（相手が答えを持っているか、言葉が通じるか） | 人が 1〜2 人に聞く（`[人]`）。AI は質問の案、同意の説明、記録の様式を用意する |

3. **判定の基準**: 実施の前に、判定の基準を書く。実施の後に基準を動かさない。
   - 例（検索語）: 「上位 20 件のうち、関係のある資料が 5 件以上あれば当たり。2 件以下なら検索語を直す」
   - 例（データ）: 「従業員規模別の利用率が、2020〜2024 年の各年で取れれば答えられる。規模の区分が 20 人以下で切れなければ、代わりの区分を検討する」
4. **担当**: AI か人か。人の方法しかない仮説は、手順を用意して「保留（人の作業待ち）」にする。

> 💬 方法と判定の基準を示し、合意を取る（とくに、人が行う方法と、有料の資料を試しに買う必要があるもの）。

### ステップ 2: 実施（AI が行うもの）

- **試しの検索**: 検索式、データベース、条件、件数、上位の関係の有無を、`results.md` の「検索の記録」に書く。当たった検索語と、外れた検索語（なぜ外れたか: 同名の別の概念、英語と日本語の訳語の違いなど）を両方残す。RQ の `plan.md`（Q5）の検索式の出発点になる。
- **データの確認**: 項目、粒度、期間、定義、形式、ライセンス・利用規約、取得の手続きを書く。試しに取得した小さなファイルは `docs/study/pilot/samples/` に置き、出所と取得日とライセンスを `results.md` に書く（規約で再配布が許されないものは置かず、取得の手順だけを書く）。大きなデータは取得しない。
- **試しの集計**: 標準ライブラリだけで書ける小さなスクリプトを `docs/study/pilot/scripts/` に置き、入力・出力・結果を `results.md` に書く。ここで得た値は、主張の根拠にしない（RQ の工程の分析で取り直す）。
- **出典**: 予備調査で見つけ、根拠に使う可能性のある資料は、`researchkit-scan` §2 と同じ規則で `sources/S000-<NNNN>.md` に登録する（`$RK sources next 000`）。実在を確かめる手順も同じである。
- サブエージェントに任せるときは、仮説ごとに分け、出典 ID の範囲を分ける（steering「サブエージェントに任せるとき」）。

### ステップ 3: 実施（人が行うもの）

- 試しの質問は、`plan.md` に、対象者の条件、質問の案、同意の説明（目的、記録の方法、匿名化、やめてよいこと）、記録してほしいこと（答えにくかった問い、言葉が通じなかった問い、答えを持っていなかった問い）を書く。
- 個人を特定できる情報は記録しない。結果は、対象者を `P01` のような記号で表して `results.md` に書き写す（steering の基本原則 9）。倫理審査が要るかもしれないとき（RP9）は、試しの質問の前に `[人]` の確認を置く。
- 結果を受け取るまでは「保留（人の作業待ち）」とし、立ち上げを止めない。

### ステップ 4: 判定と逆流

[templates/results.md](templates/results.md) の様式で `docs/study/pilot/results.md` に書く。仮説ごとに次のどれかに判定し、根拠を書く。判定は `hypotheses.md` の「答えられるか（R6）」にも写す。

| 判定 | 意味 | 動作 |
|---|---|---|
| 答えられる | 判定の基準を満たした | そのまま R7 に引き継ぐ |
| 直した | そのままでは答えられないが、答えられる形に直した | 下の「逆流」の手順で直し、直した版で確かめ直す |
| 保留 | この段階では判定できない（人の作業待ち、有料の資料の購入待ち） | 確かめる時期と方法を書く（例: 「001 の Q8 の前に `[人]` が購入して確かめる」） |
| 答えられない | 期限・予算・アクセスの範囲で、答える証拠がない | 下の「逆流」の手順で直すか、仮説を取り下げる案を作る |

**逆流**（「直した」「答えられない」のとき）:

1. 原因を書く（データの粒度が足りない、定義が違う、期間が足りない、検索語が別の概念に当たる、相手が答えを持っていない）。
2. 直し方の案を作る。仮説の範囲を絞る、代わりの指標（代理変数）にする、定義をそろえる、手法を変える見込みにする、葉を `backlog.md` に送る、のどれか。**見えた値に合わせて、仮説の向きや境目を変えない。**
3. 合意を取って、`hypotheses.md`（必要なら `issue-tree.md`）を直す（`researchkit-hypothesis` の更新モードの規則。ID を振り直さない）。直した箇所を両方の「変更の記録」と `results.md` の「逆流の記録」に書く。
4. 直した版で、同じ仮説を確かめ直す。
5. **同じ仮説で 2 回続けて「答えられない」になったら止まる。** 直し方の候補（問いの立て方を変える〈R3〉、範囲を変える〈R4〉、仮説を取り下げて決定を別の葉で支える）と推奨案を示して、ユーザーに判断を仰ぐ。自動モードでも止まる。
6. すべての仮説で主な証拠が手に入らないと分かったときも止まる（`researchkit-bootstrap` §6）。

### ステップ 5: R7 と RQ の工程への引き継ぎ

`results.md` の「わかったこと」に、次をまとめる。

- 当たった検索語とデータベース（RQ の `plan.md` の検索式の出発点）
- 手に入るデータの形式、粒度、ライセンス、取得の手続き（`researchkit-method` の手法の 3 案の根拠と、`000-research-foundation` のデータの目録の材料）
- 手に入らないと分かったデータ源（R7 の案に入れない）
- `[人]` の作業の見込み（購入、申請、倫理審査、試しの質問の続き）
- 1 件の RQ の収集に要る Web 検索の見込み（試しの検索の件数から。`config.yaml` の `session.estimates` の `Q8`・`rq` を変える材料。変えるのは R7 か R9 で行う）

## 4. 出力と記録

| ファイル | 内容 |
|---|---|
| `docs/study/pilot/plan.md` | 仮説ごとの確かめること、方法、判定の基準、担当 |
| `docs/study/pilot/results.md` | 判定、根拠、検索の記録、逆流の記録、わかったこと |
| `docs/study/pilot/scripts/` | 試しの集計のスクリプト（コミットする） |
| `docs/study/pilot/samples/` | 試しに取得した小さなデータ（再配布が許されるものだけ） |
| `docs/study/hypotheses.md`、`issue-tree.md` | 「答えられるか（R6）」の欄、逆流での修正 |
| `sources/S000-*.md` | 予備調査で見つけ、根拠に使う可能性のある出典 |

`researchkit-bootstrap` から呼ばれたときは、bootstrap がコミットする。単独で実行したときも同じ形で記録する。

```bash
git add -A
git commit --allow-empty -m "docs(bootstrap): R6 予備調査で問いを確かめる" -m "Researchkit-Bootstrap: R6"
```

R6 の完了の条件は、対象のすべての仮説が「答えられる」「直した（確かめ直して答えられる）」「保留（確かめる時期と方法つき）」のどれかであることである。「答えられない」が残っている間は完了にしない（取り下げた仮説は対象から外れる）。R6 の後に追加で確かめたときは、subject を `docs(study): 仮説 H<n> の予備調査` にし、trailer を付けない。

## 5. 省くとき（`--skip <理由>`）

RQ が 1〜2 件で済む小さな調査、すでに同じデータで答えた経験がある調査、期限が非常に短い調査では、予備調査を省いてよい。

1. `plan.md` を作らず、`results.md` だけを作る。冒頭の「省略」の節に、省いた理由と、省いたことで残る危うさ（例: 「データの粒度を確かめていない。RQ の Q5 で最初に確かめる」）を書く。
2. `hypotheses.md` の「答えられるか（R6）」は `未確認` のままにする。
3. 上の形で R6 を記録する（省いた判断も完了として記録する）。
4. 理由が引数にないときは、対話モードでは理由を聞き、自動モードでは省かない（`researchkit-bootstrap` §4「R6」）。
5. 省いたことを `docs/auto-decisions.md`（自動モード）か完了報告（対話モード）に書く。見直しの優先度は「中」にする。

## 6. 自動モード（`--auto`）

`researchkit-bootstrap` の `--auto`・`--oneshot` から呼ばれたときは、bootstrap §7 の規則に従う。単独の `--auto` も同じ扱いにする。

| 論点 | 自動モードでの動作 |
|---|---|
| 方法と判定の基準 | 推奨案を採用する。検索語は「上位 20 件のうち関係のある資料が 5 件以上」を既定の当たりの基準にする |
| 人が行う方法しかない仮説 | 資料を用意して「保留（人の作業待ち）」にし、見直しの優先度を「高」にする |
| 有料の資料を試しに買う必要がある仮説 | 買わない。「保留（購入の判断待ち）」にし、`[人]` の候補に挙げる |
| 1 回目の「答えられない」 | 推奨の直し方（範囲を絞る、代わりの指標）で `hypotheses.md` を直し、確かめ直す。問いの立て方（`framing.md`）や前提（`premises.md`）の変更が要る直し方は採らず、止まる |
| 同じ仮説の 2 回続けての「答えられない」 | 止まる（ステップ 4） |

自動で決めたことは `docs/auto-decisions.md` の「R6」の節に書く。

## 7. 完了報告

- 仮説ごとの判定（答えられる / 直した / 保留 / 答えられない）と根拠の要約（省いたときは、その理由と残る危うさ）
- 逆流させた修正（`hypotheses.md`・`issue-tree.md` のどこを変えたか）
- 保留の仮説と、確かめる時期と方法（人の作業が要るもの）
- 当たった検索語、手に入るデータ、手に入らないデータ
- 登録した出典の件数と、使った Web 検索の件数
- 次の案内: `researchkit-method`（bootstrap の中なら R7 に進む）

## 8. 規則

- 判定の基準を、結果を見てから変えない。変えるなら、計画を書き直して確かめ直し、そのことを「逆流の記録」に書く。
- 予備調査の値を、仮説の支持・棄却の根拠や、主張の根拠にしない。
- 見えた値に合わせて、仮説の向きや境目を変えない。
- 予備調査を本調査にしない。1 つの仮説にかける手間は、数件の検索と 1 つのデータの確認、1 回の試しの集計までを目安にする。
- 応答と成果物は、プロジェクトの言語ルール（`.kiro/steering/language.md`）に従う。
