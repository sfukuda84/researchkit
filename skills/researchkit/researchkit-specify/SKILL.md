# researchkit-specify スキル（Q2: 問いの仕様）

RQ の概要を、**何に、どの形で答えれば決定の役に立つか**の仕様にする。調査でいちばん高くつく失敗は、正しく調べた答えが決定に使えないことである。仕様は、調べ方（HOW）ではなく、答え（WHAT）と、その答えがなぜ要るか（WHY）に集中する。

ステップ番号、モード、質問の規則は [`researchkit-worktree`](../researchkit-worktree/SKILL.md) に従う。通常は [`researchkit-question`](../researchkit-question/SKILL.md) か [`researchkit-all`](../researchkit-all/SKILL.md) から呼ばれる。チェックポイント（Q2）は呼び出した統括スキルが記録する。単独で実行したときは、最後に `$HELPER checkpoint <RQ_NAME> Q2 "<『ステップ番号』の節の subject>"` を記録する。パスは `.researchkit/config.yaml` の `paths` で読み替える。

## 1. 対象と入力

引数の RQ を `$HELPER resolve <query>` で `RQ_NAME` に決める。作業場所は、その RQ の worktree（`$HELPER state <RQ_NAME> --phase design` の `WORKTREE_DIR`）である。worktree がなければ、`researchkit-question` から始めるよう案内する。以下、`studies/<RQ_NAME>` を `RQ_DIR` と書く。

| 入力 | 使い方 |
|---|---|
| `docs/questions/<RQ_NAME>.md` | 主な入力。問い、つながる決定と仮説、答えの形、範囲、想定する情報源、人の作業の見込み、`**手法**`、`**依存**` |
| `docs/concept/seed.md` | 読み手と決定（`D1`〜）。決定の文言をそのまま引く |
| `docs/concept/premises.md` | 前提 `RP1`〜`RP12`（範囲、期限、要求する確度、倫理など）。仕様の既定値の出どころにする |
| `docs/study/issue-tree.md`、`hypotheses.md` | この RQ が担うイシューツリーの節（`I1.2` など）と仮説（`H1` など） |
| `docs/scan/wide.md`、`docs/study/pilot/` | 用語の使われ方、データの所在、予備調査で分かった答えられる範囲 |
| `docs/glossary.md`、憲章、`docs/quality.md` | 用語の正典、確度の段階、要求する確度の水準 |
| 依存する RQ の `findings.md` | 前提として使う答え（主張 ID で参照する） |
| 引数・プロンプトの追加指示 | RQ の概要より優先する。食い違うときは確かめる |

RQ の概要がなく、追加指示もない場合は、何を問うかを質問する。答えても決定が変わらない問いになりそうなときは、`researchkit-questions` での見直しを勧める（基本原則 3）。

## 2. 手順

1. テンプレート [`templates/spec.md`](templates/spec.md) を `RQ_DIR/spec.md` に写す。すでにあれば、上書きせずに更新する。
2. 次の順に埋める。各節の書き方は §3 に従う。
   1. **問い**: 1 文の疑問文にする。大きい問いは、答えの形が異なる単位で小問 `SQ1`〜 に分ける（多くて 5 個）。小問は、イシューツリーの節と対応させる。
   2. **つながる決定**: `D1` などを引き、「答えが X なら〜を選ぶ、Y なら〜を選ぶ」の形で、答えと決定の分かれ目を書く。分かれ目を書けない問いは、決定につながっていない。
   3. **つながる仮説**: `H1` などを引き、仮説の要旨と、この RQ で確かめる部分を書く。反証条件の中身は `hypotheses.md` を正とし、ここには写さない（Q5 の `plan.md` で、観測できる形に具体化する）。
   4. **答えの形**: 小問ごとに、答えの型（§3）、単位、粒度、求める確度を書く。
   5. **判定の基準**: `AC1`〜 で、「どうなれば答えが出たとするか」と「どうなれば答えが出ないと結論するか」を書く。
   6. **範囲と範囲外**: 対象、地域、期間、母集団と、意図して扱わないものを書く。
   7. **用語**: 問いに出る語のうち、読み方が分かれうる語の定義を書く。用語集にある語は参照だけにする。
   8. **前提と依存**、**人の作業の見込み**
3. 決まっていないことは、推測で埋めずに `[NEEDS CLARIFICATION: <具体的な問い>]` を置く。ただし、前提（`RP`）、品質基準、予備調査から妥当な既定値が決まるものは既定値で埋め、「前提と依存」に「既定値として置いた」と書く。印は全体で 3 個までにし、影響の大きい順（範囲 ＞ 決定とのつながり ＞ 答えの形 ＞ 用語）に残す。残りは Q3・Q4 の明確化に回す。
4. §4 の点検を行い、満たさない項目を直す（最大 3 巡）。直せない項目は、仕様の末尾の「点検の残り」に書き、完了報告で示す。
5. `[NEEDS CLARIFICATION]` が残っていれば、通常モードでは、選択肢と推奨案（`**Recommended:**`）を添えてまとめて質問し、回答で置き換える。自動モードでは推奨案を採り、`RQ_DIR/auto-decisions.md` に記録する。Q3・Q4 で扱う方がよい細部の論点は、印のまま残してよい。
6. RQ の概要（`docs/questions/<RQ_NAME>.md`）と食い違う決定をしたときは、概要の側も直す（基本原則 10）。

## 3. 書き方

### 答えの形

読み手が決定に使える形を、小問ごとに 1 つ選ぶ。型を決めると、Q5 の分析の計画と Q10 の主張の書き方が決まる。

| 型 | 使う場面 | 書くこと | 例 |
|---|---|---|---|
| 数値と幅 | 規模、割合、伸び率、価格 | 指標、単位、時点、点推定と幅（範囲か信頼区間）、許す誤差 | 2025 年の国内市場規模（億円、名目）。幅を付け、推計の方法の違いを示す |
| 比較表 | 選択肢や競合の比較 | 比べる対象、比べる軸、軸ごとの尺度（数値・段階・有無） | 候補 3 社を、価格・対応地域・導入実績の 3 軸で比べる |
| はい／いいえと条件 | 可否、有無、規制への該当 | 判定の文、はいになる条件、いいえになる条件、「分からない」の扱い | 〇〇は 2026 年時点で規制の対象か。対象になる条件を示す |
| 類型 | ニーズ、行動、事例の分類 | 分類の軸、類型の数の目安、各類型に要る根拠の数 | 利用をやめた理由を 3〜6 の類型に分け、各類型に 2 人以上の発言を付ける |
| そのほか | 時系列の傾向、順位、因果の説明など | 型の名前と、上の 4 つと同じ粒度の書くこと | 過去 10 年の推移と転換点 |

- 求める確度は、憲章の段階（既定: `確実`／`可能性が高い`／`示唆`／`不明`）で書く。品質基準 `docs/quality.md` の要求より低くしない。
- 因果を問う小問（「〜は〜の原因か」）は、確かめられる確度の上限を、手法を決める前に意識する。観察データだけで因果を `確実` にすることは、ふつうできない。上限が決定に足りないなら、問いを「関連があるか」に弱めるか、Q5 で手法を足すことを `[NEEDS CLARIFICATION]` にする。

### 判定の基準

- **答えが出た**とする条件を、観測できる形で書く。例: 「等級 B 以上の互いに独立した出典 2 件以上で、規模の推計が得られる」「インタビュー 8 人以上で、新しい類型が出なくなる（飽和）」。
- **答えが出ない**と結論する条件も書く。例: 「公的統計と業界団体の資料に該当の区分がなく、有料レポートも入手できない」。この場合も結果であり、`findings.md` の「残った問い」に書く（基本原則 6）。
- **探すのを止める**条件を書く。例: 検索を `plan.md` の全データベースで終えた、新しい出典が 2 回続けて既知のものだけだった。止める条件がないと、収集が終わらない。
- 仮説の支持・不支持の条件は、ここではなく `plan.md` の反証条件に書く。判定の基準は、仮説の向きにかかわらず答えが出たかを決める。

### 範囲と範囲外

- 範囲には、対象（何を）、地域、期間（データの期間と、答えの時点）、母集団（誰を・どの企業を）を書く。前提 `RP` の範囲を既定にする。
- 範囲外には、読み手が含むと思いそうだが扱わないものを書く。例: 「海外市場」「法人向けの利用」「2020 年以前の推移」。理由を短く添える。

### 用語

- 読み方が分かれる語は、**操作的定義**（何をどう数えれば、その語に当たるか）で書く。例: 「利用者 = 直近 30 日に 1 回以上ログインした個人」。
- 定義が定まらない語は `[NEEDS CLARIFICATION]` にし、Q4 で決める。決まった定義は、ほかの RQ でも使うなら `docs/glossary.md` に足す。

## 4. 仕様の点検

ファイルには書き出さず、次の項目で点検する（Clarify の各回の後にも同じ項目で見直す）。

- [ ] 問いが 1 文の疑問文で、答えの形が分かる
- [ ] つながる決定が `seed.md` の `D` にあり、答えと決定の分かれ目が書かれている（000・999 を除く）
- [ ] つながる仮説が `hypotheses.md` の `H` にある（仮説のない探索型の RQ では「なし（探索型）」と理由がある）
- [ ] すべての小問に、答えの型、単位、粒度、求める確度がある
- [ ] 判定の基準に、答えが出た条件、答えが出ない条件、探すのを止める条件がある
- [ ] 範囲（対象・地域・期間・母集団）と範囲外が書かれている
- [ ] 手法、データベース名、検索式、ツールを書いていない（Q5 に回す）
- [ ] 曖昧な形容（「主要な」「大手の」「最近の」「多くの」）に、定義か数の基準がある
- [ ] `[NEEDS CLARIFICATION]` が 3 個以下
- [ ] 憲章・品質基準・前提と矛盾しない

## 5. 000 と 999 の扱い

予約番号の RQ は、テンプレートの節を次のように読み替える（steering の「RQ の工程」の注記）。

| 節 | `000-research-foundation`（主張を作らない基盤づくり） | `999-research-report`（統合報告） |
|---|---|---|
| 問い | 「この調査の共通基盤は、各 RQ が使える状態に整っているか」 | 「すべての RQ の答えを合わせると、決定 `D1`〜 に何が言えるか」 |
| 小問 | 出典台帳、用語集、データの目録、分析環境、検索ログの形式の 5 つ | 決定ごと、または `docs/questions/999-research-report.md` の構成の章ごと |
| つながる決定・仮説 | `—`（基盤なので書かない） | すべての `D` と、各 RQ が確かめた `H` |
| 答えの形 | 基盤ごとの完成条件の一覧（例: `commands.analysis` で試しのスクリプトが動き、`out/` に JSON が出る） | `999-research-report.md` の読み手・形式・構成。エグゼクティブサマリー、確度つきの結論、限界、次の問い |
| 判定の基準 | 各基盤の完成条件が満たされている。000 では主張を作らないので、答えが出ない条件は書かない | すべての RQ の主張が、報告の結論のどこかに反映されるか、採らない理由が書かれている。報告の数値がすべて出力ファイルか主張にたどれる |
| 範囲外 | 個別の RQ の収集と分析 | 新しい収集（足りない根拠は、新しい RQ として `researchkit-questions` に戻す） |

## 6. 完了報告

- `RQ_DIR/spec.md` のパス
- 問い、小問の数、答えの型、判定の基準の要約
- 既定値として置いたこと、残っている `[NEEDS CLARIFICATION]`
- 点検の結果（満たさない項目があれば、その内容）
- 次の案内: `researchkit-clarify <RQ_NAME> --round 1`（Q3）
