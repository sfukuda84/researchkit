# researchkit-framing スキル（R3: 問いの立て方の 3 案 → 選択）

同じ種から、答えの形と必要な証拠が違う 3 つの問いの立て方を作って比べる（3 案を同じ観点で比べて 1 つを選ぶ）。問いの立て方は、後の手法、証拠、期間をほぼ決めてしまう。ここで選んだ立て方が、壁打ち（R4）とイシューツリー（R5）の出発点になる。

パスは `.researchkit/config.yaml` の `paths` で読み替える。進捗の記録とモードは [`researchkit-bootstrap`](../researchkit-bootstrap/SKILL.md) の §3・§7 に従う。

## 1. 入力

- `docs/concept/seed.md`（決めたいこと D1〜、何が分かれば何を決められるか、問いの言い換え案、選択）
- `docs/scan/wide.md`（すでに分かっていること、まだ分かっていないこと、データの所在、用語の定義の揺れ、論点と立場、問いへの影響）
- 引数の希望

どちらかがなければ、欠けている工程（`researchkit-seed` / `researchkit-scan`）を案内する。`wide.md` の「問いへの影響」を最初に読む。

## 2. 問いの型

| 型 | 中心の問いの形 | 答えの形 | 主に要る証拠 | 向いている場面 |
|---|---|---|---|---|
| 記述型（実態把握） | 〇〇はどうなっているか。どれだけあるか | 数値、分布、一覧 | 統計、調査データ、網羅的な収集 | 規模や現状が分からないと決められない |
| 探索型 | 〇〇について、何が起きているか。どんな要因がありうるか | 論点・要因・類型の一覧（確度は低くてよい） | 文献、インタビュー、事例 | 先行の調査が少なく、仮説を立てる材料がない |
| 仮説検証型 | 〇〇は△△か（はい・いいえ） | 仮説の支持・棄却と確度 | 反証条件に当たるかを判定できるデータ・文献 | 有力な仮説があり、それで決定が分かれる |
| 比較評価型 | A と B（と C）のどれが、基準 X でよいか | 基準ごとの比較の表と推奨 | 同じ基準で測った各選択肢の証拠 | 選択肢が決まっていて、どれかを選ぶ |
| 因果推論型 | 〇〇は△△を引き起こすか。どれだけ変えるか | 効果の向きと大きさ、その確度 | 比較群のあるデータ、実験、自然実験、因果の識別の前提 | 施策の効果で決定が分かれる |
| 予測型 | 〇〇は将来どうなるか | 予測値と幅、前提ごとのシナリオ | 時系列のデータ、前提の根拠 | 将来の値で決定が分かれる |

- 因果推論型は、相関から因果を言わないために、比較群の作り方（実験、差分の差分、回帰不連続など）と識別の前提が書けるときだけ候補にする。書けなければ、記述型か仮説検証型に落とし、「因果は言わない」と範囲外に書く。
- 1 つの調査で型を混ぜてよい（例: 記述型で規模を測り、比較評価型で選ぶ）。その場合は、主な型と従の型を書く。

## 3. 手順

### ステップ 1: 決定から型を当てる

`seed.md` の「何が分かれば何を決められるか」の各行について、規則の左辺（調べる対象）がどの型の答えで埋まるかを当てる（例: 「市場が 100 億円以上か」は記述型か仮説検証型、「A と B のどちらの価格が売れるか」は比較評価型か因果推論型）。`wide.md` の「すでに分かっていること」で埋まる左辺は、型を当てずに「既存の調査で足りる」と書く。

### ステップ 2: 3 案を作る

候補から、**答えの形と必要な証拠が互いに違う 3 案**を選ぶ。

- 3 案は、型、範囲（地域・期間・対象）、主な証拠のうち、少なくとも 2 つが違うようにする。
- 1 案は、`seed.md` で選んだ問いに最も忠実な案にする。
- 1 案は、`wide.md` の「まだ分かっていないこと」を最も強く狙う案にする（すでに答えがある部分を調べ直さない）。
- 1 案は、期間と費用を最も小さくし、公開の情報だけで期限内に答えが出せる案にする（ほかの 2 案のどちらかと兼ねてもよい。そのときは残りの 1 案を自由にする）。

案ごとに、次を書く。

| 項目 | 内容 |
|---|---|
| 一言 | この案を 1 文で |
| 型 | 主な型（と従の型） |
| 中心の問い | 疑問文。答えの形が分かるように |
| 下位の問い | 中心の問いに答えるために答える問い（2〜5 個。R5 のイシューツリーの第 1 層の候補） |
| 答えの形 | 何が書かれていれば答えたと言えるか（数値と幅、はい・いいえと確度、比較の表、要因の一覧） |
| 決定への効き | どの D の、どの選択肢の判断が、答えでどう変わるか |
| 必要な証拠 | 種類（統計、文献、自社データ、インタビュー）と、`wide.md` で所在が分かっているか |
| 主な手法の見込み | デスクリサーチ / 文献レビュー / データ分析 / 定性調査（R7 で決める。ここでは見込み） |
| 範囲 | 地域、期間、対象、比較の対象 |
| 期間・費用 | 目安（何週間、有料の資料、人の作業の量） |
| リスク | 答えが出ない、証拠が手に入らない、偏る、などの危うさと、そのときの症状 |
| 答えが出ないときの扱い | 部分的な答えでも決定に使えるか。代わりの指標 |

PICO（Population 対象、Intervention 介入・要因、Comparison 比較、Outcome 結果。根拠に基づく医療で使われる問いの分け方）で要素に分けられる問い（効果、要因、比較を問う問い）は、案の表に PICO の分解を添える。範囲と比較の対象の抜けが見つかりやすい。

### ステップ 3: FINER で点検する

各案の中心の問いを、FINER の基準（Hulley らが臨床研究の設計の教科書『Designing Clinical Research』で示した、良い研究の問いの条件）で ◎／○／△ に点検する。調査に合わせて、次のように読み替える。

| 基準 | 読み替え |
|---|---|
| Feasible（実行できる） | 期限・予算・手に入る証拠で答えが出せるか |
| Interesting（関心がある） | 読み手が答えを知りたいか |
| Novel（新しい） | `wide.md` で、すでに答えがない部分を扱うか |
| Ethical（倫理的） | 人を対象にする調査で、同意と匿名化が守れるか。利用規約に反しないか |
| Relevant（意味がある） | 決定（D）につながるか |

△ が 2 つ以上ある案は、直すか、比較の表に「弱い」と明記する。

### ステップ 4: 比較して提示する

3 案を比較表にまとめ、推奨案と理由を添えて示す。比較の観点は次の 6 つ。

1. 決定への効き（どれだけ多くの D の判断を、どれだけ確かに変えられるか）
2. 必要な証拠の手に入りやすさ（`wide.md` の所在、有料、申請）
3. 期間・費用（期限に対して）
4. リスク（答えが出ない、偏る、倫理）
5. すでに分かっていることとの重なりの少なさ
6. 答えの形の明確さ（判定できるか）

決定への効きを最も重く見る。答えても決定が変わらない案は、ほかが優れていても推奨しない（steering の基本原則 3）。

### ステップ 5: 選択

- **対話モード**: AskUserQuestion で案を選んでもらう。推奨案を先頭に `(Recommended)` 付きで置く。「組み合わせる」（例: A の範囲で C の型）も受け付け、組み合わせた案を 1 つにまとめ直して、もう一度確かめる。
- **自動モード**: 推奨案を採用し、`docs/auto-decisions.md` に記録する。型の選択と範囲は、見直しの優先度を「高」にする。決定への効きが同じなら、期間と費用が小さい案を採る。

選んだ案を `framing.md` の「選択」に書く。選ばなかった案は消さず、`docs/concept/backlog.md` にも要点を残す（後で問いの候補として拾えるように。様式は `researchkit-sparring` の [templates/backlog.md](../researchkit-sparring/templates/backlog.md)）。

## 4. 出力

- `docs/concept/framing.md`（様式: [templates/framing.md](./templates/framing.md)）
- `docs/concept/backlog.md`（選ばなかった案の要点を追記）

終わったら `researchkit-bootstrap` §3 の形で `R3` を記録する（単独で実行したときも記録する）。

## 5. 完了報告

- 3 案の一言と型、選んだ案（組み合わせた場合はその内容）
- 選んだ案の中心の問い、答えの形、下位の問い、決定への効き
- FINER の点検で弱かった点と、その扱い
- 次の案内: `researchkit-sparring`（R4）

## 6. 規則

- 事実（市場の大きさ、先行研究の結論）を案の中で新しく書かない。書くときは `wide.md` の出典を引く。
- 「〇〇について調べる」のような、答えの形がない問いを中心の問いにしない。
- 因果を問う案は、識別の前提を書けないかぎり推奨しない。
- 応答と成果物は、プロジェクトの言語ルール（`.kiro/steering/language.md`）に従う。
