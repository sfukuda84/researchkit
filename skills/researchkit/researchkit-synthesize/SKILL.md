# researchkit-synthesize スキル（999 の Q8: 統合報告）

各 RQ の主張を、読み手の決定に答える 1 つの報告にまとめる。報告は**結論から書き**、結論の下に理由を、理由の下に各 RQ の主張を置く。ここでは調べない。材料は各 RQ の `findings.md` だけである。

パスは既定の配置で書いている。`.researchkit/config.yaml` の `paths` で読み替える。ステップ番号、`$HELPER`、再開、自動モードの共通の規則は [`researchkit-worktree`](../researchkit-worktree/SKILL.md) に従う。`$RK`・`$CHECK`・`$NUM` の意味は steering（`.kiro/steering/research.md`）の「エージェントの行動規範」のとおりである。

## 0. 大原則

- **新しい事実を足さない。** 報告の事実の文は、すべて各 RQ の主張（`<NNN>-C<n>`）に戻れるようにする。主張にない事実が要ると分かったら、報告に書かずに「限界」と「次の問い」に書く。Web 検索はしない。
- **確度を上げない。** 結論の確度は、それを支える主張の確度を超えない（§4）。統合したことで確かになったように書かない。
- **結論を先に書く。** 読み手が最初の 1 ページで、何が分かり、何を決められ、何が分からないかをつかめるようにする。
- **都合の悪い主張を落とさない。** 結論に反する主張、棄却された仮説、`不明` のまま残った問いも、限界か本文に書く。
- **数値は主張と同じ値を、同じ出力ファイルの参照つきで写す。** 丸めるときは「約」を付ける。RQ をまたいで新しく計算した数値は `{N:calc}` を付け、「計算」の節に式と入力（主張の ID）を書く。

## 1. 引数

```text
$ARGUMENTS
```

- `--auto` は自動モード（§5）。
- 対象は常に `999-research-report` である。ほかの RQ の番号が指定されたら、`researchkit-findings` を案内する。

## 2. 入力と前提

| 入力 | 用途 |
|---|---|
| `studies/*/findings.md`（000 と 999 を除く） | 統合の材料（主張、答え、仮説の判定、残った問い） |
| `docs/concept/seed.md` | 読み手、決めたいこと（`D1`〜）、期限、答えの使い道 |
| `docs/questions/999-research-report.md`、`studies/999-research-report/spec.md`・`plan.md` | 報告の読み手・形式・構成・言語 |
| `docs/study/hypotheses.md`、`issue-tree.md` | 仮説の最終の判定、問いの構造（キーラインの材料） |
| `docs/questions/README.md`、各 RQ の概要 | RQ の状態（`完了`／`人の作業待ち`）、つながる決定 |
| `docs/concept/premises.md` | 範囲、要求する確度、利害関係 |
| 憲章、`docs/quality.md` | 確度の段階、AI 利用の開示、報告の品質基準 |

- ほかのすべての RQ が `完了` か `人の作業待ち` でなければ始めない（`$HELPER ensure` が `DEPENDENCY_PENDING` で止める）。
- 始める前に `$CHECK --all` と `$NUM --all` を実行する。ほかの RQ に ERROR があれば止まり、その RQ の見直しを案内する（報告で誤った主張を広げないため）。
- 報告の言語は、言語ルールの例外により `999-research-report.md` の「読み手」と「形式」に従う。

## 3. 手順

### ステップ 1: 主張の棚卸し

全 RQ の主張を 1 つの表にする（RQ、主張の ID、主張、確度、つながる決定、つながる仮説）。あわせて、各 RQ の「答え」、仮説の判定、「残った問い」を集める。`人の作業待ち` の RQ は、残っている `[人]` のタスクと、それで答えが変わりうる主張に印を付ける。

### ステップ 2: 決定との対応

決めたいこと（`D1`〜）ごとに、つながる RQ と主張を並べる。

- 主張が足りない決定は、そのことを限界に書く（ここで補わない）。
- 主張どうしが食い違う組（同じ量の値が違う、向きが逆）を挙げる。食い違いは、範囲・時点・定義の違いで説明できるかを主張の「反証・限界」から確かめ、説明できなければ両方を書いて、確度の低い方に寄せないまま「判断を変える条件」に書く。

### ステップ 3: ピラミッド構造を組む

Barbara Minto のピラミッド原則（『The Pyramid Principle』）に沿って、結論から下へ組む。

1. **導入（状況・複雑化・問い）**: 読み手が知っている状況、それを揺るがす複雑化、そこから生じる問いを、各 1〜2 文で書く。問いは `seed.md` の決めたいことと同じものにする。
2. **頂点（結論）**: 問いへの答えを 1〜2 文で書く。決定に向けた推奨か、判断の材料かは、`seed.md` の「答えの使い道」に合わせる。
3. **キーライン**: 頂点を支える理由を 2〜5 個にする。互いに重ならず、合わせて漏れがない（MECE）ようにまとめる。理由のまとめ方は、帰納（同じ種類の理由を並べる）か演繹（前提 → 前提 → 結論）のどちらかに揃える。
4. **支え**: 各キーラインの下に、それを支える各 RQ の主張（`<NNN>-C<n>`）を置く。どのキーラインにも入らない主張は、問いに関係がなければ付録の一覧にだけ置き、関係があるのに入らなければ構造を組み直す。
5. **縦の確かめ**: 上の文を読んだ読み手が「なぜ」「どうして分かる」と問い、下の文がそれに答えているかを確かめる。

### ステップ 4: 結論の確度

- 結論とキーラインに確度を付ける。段階は憲章（`confidence.levels`）のものを使う。
- 結論の確度は、**欠けると結論が成り立たない主張のうち最も低い確度**を超えない。独立した複数の主張が同じ結論を支えるときも、そのうち最も高い主張の確度を超えない。
- `人の作業待ち` の RQ の主張に頼る結論は、その旨を限界に書く。
- 結論ごとの確度と根拠を、付録の「結論の表」に主張の書式（steering）で書く（ID は `C1`〜、根拠は `<NNN>-C<n>`）。Q10（`researchkit-findings` の統合モード）が、この表を `studies/999-research-report/findings.md` に写して整合を確かめる。

### ステップ 5: 決定ごとの答え

決定（`D1`〜）ごとに、答え（推奨、または判断の材料）、確度、根拠の主張、**判断を変える条件**（どの前提が崩れたら答えが変わるか。主張の反証・限界と、保留の仮説から書く）を書く。決定を下すのは読み手であり、報告は判断に必要なものを揃える。

### ステップ 6: エグゼクティブサマリー

報告の最初に置く。1 ページ（目安 400〜800 字）に収める。

1. 結論（1〜2 文と確度）
2. 決定ごとの答え（表）
3. 主な理由（キーラインを 1 行ずつ）
4. 主な限界と、判断を変える条件
5. 次の一歩

サマリーにも、本文にない事実を書かない。

### ステップ 7: 限界と次の問い

- **限界**: 範囲（地域・期間・対象）、手法の限界（標本の大きさ、推計の前提）、`不明` のまま残った問い、棄却・保留の仮説、`人の作業待ち` の RQ、RQ どうしの食い違い、主張が足りない決定。
- **次の問い**: 各 RQ の「残った問い」と、統合で見えた空白を、決定への効き方の大きい順に並べる。`docs/concept/backlog.md` にも足す。

### ステップ 8: 書き出しと検証

1. [templates/report.md](./templates/report.md) の様式で `reports/report.md` を書く。事実の文には `（<NNN>-C<n>）` を添える。数値の参照は、主張の `{N:analysis/out/...}` をリポジトリのルートからの相対パス `{N:studies/<NNN-name>/analysis/out/...}` に直して写す。
2. 付録の「出典」には、報告が参照した主張の根拠の出典（ID、書誌、URL か DOI、参照日）を `sources/` から写す。写した出典の `used_in` に `"999"` を足す（`check.py` は `reports/` の参照を RQ `999` の参照として数え、`used_in` と食い違うと WARN を出す）。
3. AI 利用の開示を、憲章の定めのとおりに書く。
4. `$CHECK --file reports/report.md` と `$NUM --file reports/report.md` を実行し、ERROR を 0 件にする。
5. `studies/999-research-report/tasks.md` の統合のタスクを `- [x]` にする。

## 4. 規則

- 報告に、どの主張にもつながらない事実の文を書かない。一般的な背景の説明（用語の定義など）は、`docs/glossary.md` の定義を使う。
- 本文で確度をぼかさない。確度の言葉は憲章の段階だけを使う。
- 各 RQ の `findings.md` は、このスキルでは書き換えない。誤りに気づいたら、報告でその主張を使わないか限界に書き、完了報告でユーザーに伝える。
- 読み手が意思決定者なら、専門用語を減らし、方法の詳細は付録に回す。

## 5. 自動モード（`--auto`）

| 場面 | 自動モードでの動作 |
|---|---|
| キーラインのまとめ方、導入の書き方 | 推奨案を採用する |
| 食い違う主張の扱い | 両方を書き、結論の確度を低い方に合わせる。`studies/999-research-report/auto-decisions.md` に記録する |
| 主張の足りない決定 | 答えを書かずに限界に書き、記録する |
| ほかの RQ の ERROR、主張の誤り | 止まる |

## 6. 出力

- `reports/report.md`（様式: [templates/report.md](./templates/report.md)）
- `docs/concept/backlog.md` に足した次の問い
- `studies/999-research-report/tasks.md` の `- [x]`

次の工程は `researchkit-publish`（999 の Q9。読み手に合わせた形式）である。チェックポイントは呼び出し元（`researchkit-execute`・`researchkit-all`）が記録する。単独で実行したときは、最後に `$HELPER checkpoint 999-research-report Q8 "<『ステップ番号』の節の subject>"` を記録する（`researchkit-worktree`）。

## 7. 完了報告

- 結論（1〜2 文と確度）と、決定ごとの答え
- キーラインと、それぞれを支える主張の数
- RQ どうしの食い違いと、その扱い
- 主張が足りなかった決定、`人の作業待ち` の RQ の影響
- 各 RQ の主張に見つけた誤り（あれば。その RQ の見直しを勧める）
- `$CHECK` と `$NUM` の結果
- 次の案内: `researchkit-publish`（999 の Q9）
