# researchkit-bootstrap スキル（調査の立ち上げ: R0 → R12）

調べたいことの 1 文から、RQ ごとの仕様化と実行（`researchkit-all`）に入れる状態（決めたいことと問い、既存の資料の地図、前提、イシューツリーと仮説、予備調査の結果、手法、憲章、RQ の一覧、共通基盤、品質基準と最終成果物の形）までを、1 つの流れで作る。各ステップの中身は、それぞれのスキルの SKILL.md に従う。**このファイルには、順番と引き継ぎだけを書く。**

パスは `.researchkit/config.yaml` の `paths` で読み替える。`$RK`、`$CHECK` の意味は steering（`.kiro/steering/research.md`）の「エージェントの行動規範」のとおり。

## 1. 引数

```text
$ARGUMENTS
```

`--auto` と `--oneshot` は実行モードの指定であり、位置を問わない。取り除いた残りを、調べたいことの 1 文（R1 の入力）か、各ステップへの追加の希望として扱う。

| 指定 | モード | 動作 |
|---|---|---|
| なし | 対話 | 各ステップのスキルの手順どおりに、ユーザーに質問し、合意を得ながら進める |
| `--auto` | 自動 | ユーザーに一度も質問せず、推奨案を採用して最後まで進める（§7） |
| `--oneshot` | 一括質問 | R0 で一度だけ、影響の大きい論点をまとめて質問する。以降は `--auto` と同じく自動で進める（§7） |

両方が指定されたときは `--oneshot` として扱う。

`--adopt` は、既存の調査に取り込んだ後（`new-researchkit-project --adopt`）に使う指定であり、位置を問わない。上のどのモードとも組み合わせられる。付けると、R0 の後に §8 の取り込みの計画を作り、ステップごとに「移し替える / 完了として記録 / 新しく作る / 飛ばす」を決めてから進める。

`--skip-pilot` は、R6 を `researchkit-pilot --skip` で実行する指定である（小さな調査で予備調査を省く。§4「R6」）。

各ステップのスキルには、自動モード・一括質問モードのとき `--auto` を付けて呼んだものとして扱う。

## 3. 進捗の記録と再開

- 各ステップが終わったら、次のようにコミットする。変更がなくても空コミットで記録する。

  ```bash
  git add -A
  git commit --allow-empty -m "<§2 の subject>" -m "Researchkit-Bootstrap: <ステップ>"
  ```

- ステップのスキルを単独で実行したとき（例: `/researchkit-seed`）も、同じ形で記録する。各スキルの出力と記録を書いた節（「出力」「出力と記録」「引数と入出力」など、スキルによって名前が違う）にある「R<n> を記録する」は、この形のコミットを指す。
- `.researchkit/usage/` はコミットしない（`git add -A` の前に `.gitignore` にあることを確かめる）。
- Claude Code のクラウドセッション（環境変数 `CLAUDE_CODE_REMOTE` が `true`）では、コミットのたびに `git push -u origin HEAD` で作業ブランチを push する。push に失敗しても止まらず、失敗したことを完了報告に挙げる。ローカルでは push しない。
- 開始時に `$RK bootstrap` で完了済みのステップ（`COMPLETED_STEPS`）と次のステップ（`NEXT_STEP`）を調べ、`NEXT_STEP` から再開する。`DONE` なら立ち上げは完了しているので、完了報告の「次の案内」だけを示す。
- 記録がなくても成果物がそろっているステップ（`--adopt` で取り込んだ調査に多い）は、内容を確かめる。対話モードでは、完了として記録してよいかをユーザーに確かめる。自動モード・一括質問モードでは確かめずに記録し、再開するステップを示すだけにする。
- 成果物が既存の別の資料にある場合（例: `企画書.md`、`proposal/`、`literature/references.bib`）は、そのステップのスキルの取り込み（更新モード）で researchkit の様式に移し替えてから記録する。元の資料は動かさない・消さない。
- 再開する場合は、完了済みのステップと再開するステップをユーザーに示してから進める。
- 予算の STOP（§4「予算の確認」）で止まった場合も、新しいセッションで同じ引数でこのスキルを実行すれば、`NEXT_STEP` から再開する。

## 4. 手順

### R0: 事前確認と初期化

1. Git リポジトリのルートで、ブランチが `main` であり、未コミットの変更がないことを確かめる。Claude Code のクラウドセッションでは、`main` の代わりにセッションの作業ブランチにいればよい。満たさない場合は、ユーザーに状況を示して対応を確かめる（自動モード・一括質問モードでは止まる。§6）。Git リポジトリでなければ、`git init -b main` してよいかを確かめてから初期化する（自動モードでは初期化する）。
2. `.researchkit/config.yaml` がなければ `$RK init` で作る。既存のファイルは変えない。
3. Claude Code で使うときは、`$RK doctor` でフックの有無を確かめ、Web 検索を数えるフックがなければ `$RK hooks install` で入れる（既存の設定は保たれる）。
4. `docs/concept/` に、`.gitkeep` 以外の入力のファイル（`core-question.md`、`seed.md` など）があることを確かめる。ない場合は、引数の 1 文を `docs/concept/core-question.md` に書く。引数にもなければ、次のように聞く（自動モードでは止まる。`--adopt` のときは聞かずに 6 へ進む）。

   > 調べたいことを 1 文で教えてください。「〇〇は△△か」という問いの形でも、「〇〇の市場に参入すべきか判断したい」という決めたいことの形でも、テーマの名前だけでも構いません。誰がその答えを使うか、いつまでに要るかが決まっていれば、それも添えてください。

5. 引数で入力への追記があれば、`core-question.md` の末尾に「追記（YYYY-MM-DD）」の節として足す。
6. `--adopt` のときは、§8 の取り込みの計画を作って合意を得る（4 の入力がなくても止まらない。既存の企画書や調査の資料を入力として扱う）。
7. `--oneshot` のときは、§7 の一括質問を行う。`--adopt` と組み合わせたときは、既存の資料から決まる論点を除いて選ぶ。
8. 変更があれば、`chore(research): researchkit を初期化` でコミットする（trailer なし）。`new-researchkit-project` で作ったプロジェクトで変更がなければ作らない。

### 予算の確認（R2・R6 の前）

R2 と R6 は Web 検索が多い。それぞれのステップに入る前に、次を実行する。

```bash
$RK budget --step R2   # R6 の前は --step R6
```

- `VERDICT: OK` なら進む。
- `VERDICT: STOP`（終了コード 4）なら、そのステップに入らずに止まる。自動モードでも止まる。これは失敗ではなく区切りである。完了報告に、完了済みのステップと、**新しいセッションを開いて**同じ引数で `researchkit-bootstrap` を実行すれば続きから再開することを書く。
- `VERDICT: UNMETERED`（回数を数えられない環境）なら進む。R2 と R6 の検索の件数を、それぞれの成果物の検索の記録に残す。
- `--skip-pilot` か、R6 を省くと決めた場合は、R6 の前の確認は要らない。

### R1〜R11

各スキルの手順を最後まで行う。ヒアリング、調査、案の比較、合意、予備調査、検証を省かない。各ステップの終わりに §3 の形で記録する。

引き継ぎの注意:

- **R0 → R1**: `core-question.md` の原文は、R1 で一字も変えずに `seed.md` に写す。一括質問の回答（§7）は R1 の「確定」の根拠になる。
- **R1 → R2**: `seed.md` の「調査の論点」と、決めたいこと（D1〜）の「何が分かれば決められるか」が、R2 の調査の問いの入力になる。
- **R2 → R3**: `wide.md` の「問いへの影響」（すでに答えがある、データが存在しない、用語の定義が割れている、など）を、R3 の案づくりで最初に扱う。すでに十分な答えがある問いは、そのまま調べ直す案にしない。
- **R3 → R4**: 選ばなかった案は `backlog.md` に残る。R4 の壁打ちで要素を拾い直してよい。
- **R4 → R2（戻り）**: 壁打ちで範囲（RP3）や決めたいこと（RP2）が大きく変わったら、R2 に戻って再調査する。対話モードでは戻るかを確かめる。自動モードでは戻らず、`docs/auto-decisions.md` に記録する。
- **R4 → R5**: RP2（決めたいこと）と RP3（範囲）の確定内容を、イシューツリーの根と枝の出発点にする。RP7（要求する確度）は、仮説の反証条件の厳しさに効く。
- **R5 → R6 → R5（戻り）**: R6 で「答えられない」「データ・文献が手に入らない」と判定した仮説は、`researchkit-pilot` の手順で `hypotheses.md`・`issue-tree.md` を直す（問いを絞る、代わりの指標にする、範囲を変える）。直した後に、もう一度 R6 の該当する仮説を確かめる。同じ仮説で 2 回続けて「答えられない」になったら、対話モードではユーザーに問いの立て方の見直し（R3・R4 に戻るか）を確かめる。自動モードでは止まる（§6）。
- **R6 → R7**: 予備調査で当たった検索語とデータベース、手に入ったデータの形式とライセンス、試しの質問で分かったことを、`researchkit-method` の手法の 3 案の比較の根拠にさせる。手に入らないと分かったデータ源を、案に入れさせない。
- **R7 → R8**: `docs/method.md` の手法（文献レビューの有無、定性調査の有無）と、RP7（要求する確度）・RP9（倫理と個人情報）・RP10（利害関係）を、憲章の出典の等級、確度の段階、倫理、利害の開示、AI 利用の開示の条項の入力として渡す。確度の段階を既定から変えたら、`config.yaml` の `confidence.levels` も合わせさせる。
- **R8 → R9**: RQ は `issue-tree.md` の葉と `hypotheses.md` の仮説から切り出し、どの RQ も `seed.md` の決定（D1〜）につなぐ。答えても決定が変わらない RQ は作らない。共通基盤と統合報告の候補は RQ にせず、R10・R11 に回す。番号 `000` と `999` は使わない。R6 で保留にした仮説に依存する RQ は、その旨を概要に書かせる。
- **R9 → R10**: 全 RQ の「想定する情報源」と `docs/method.md` の分析環境から、出典台帳・用語集・データの目録・検索ログの形式を `000-research-foundation.md` にまとめさせる。`wide.md` の用語と定義（系統 D）は、用語集の初期の項目になる。
- **R10 → R11**: RP7（要求する確度）と RP8（成果物の形式）、RP1（読み手）を、`docs/quality.md` の水準と `999-research-report.md` の読み手・形式・構成に引き継ぐ。品質基準で主張の根拠に使える最低の等級を決めたら、`config.yaml` の `sources.min_grade` も合わせさせる。
- **R7・R11 → config**: `commands.analysis` と `sources.min_grade` が成果物と食い違わないこと。
- **仮題**: R1・R4 で調査の名前（仮題）を決めたり変えたりしたら、`.researchkit/config.yaml` の `title` も更新する。

### R6: 予備調査を省くとき

- `--skip-pilot` のとき、または R4 の前提（RP4 の期限が短い、RP5 の予算が小さい、RQ が 1〜2 件で済む小さな調査）から省くと判断したときは、`researchkit-pilot --skip <理由>` で実行する。省いたことと理由を `docs/study/pilot/results.md` に書き、§3 の形で R6 を記録する（省いた判断も完了として記録する。再開のたびに聞き直さないため）。
- 対話モードで省くかどうかを AI が判断したときは、理由を示してユーザーに確かめる。自動モードでは省かない（引数に `--skip-pilot` があるときだけ省く）。
- 省いたときは、R7 の手法の比較で「予備調査で確かめていない」ことを危うさとして扱わせ、完了報告に挙げる。

### R12: 全体の検証

1. 次の検証を実行し、エラーが 0 件になるまで直す。`python3` がない環境では `python` または `py -3` に読み替える。

   ```bash
   python3 <skills>/researchkit-questions/scripts/validate.py docs/questions --require-reserved
   $CHECK --all
   $RK doctor
   ```

   - `$CHECK --all` の WARN のうち、R2・R6 で登録した `S000-*` の出典が「使われていない」というものは、RQ の工程で使われる前なので、エラーにしない。`grade: D` の出典の WARN は、その出典を根拠に使っていないことを確かめて残す。
   - `$RK doctor` の WARN（`commands.analysis` の空欄、フックがない、など）は、エラーにしない。内容を完了報告に挙げ、ソフトウェアの導入やアクセス権の申請が要るなら `[人]` の作業として案内する。

2. 次の整合を確かめる。食い違いがあれば、該当するスキルの更新モードで直すか、ユーザーに確かめる。
   - `seed.md` の決定（D1〜）と、`docs/questions/` の RQ の「つながる決定」（どの決定にも少なくとも 1 件の RQ があるか。どの RQ も決定につながっているか）
   - `hypotheses.md` の仮説と、RQ の「つながる仮説」（どの仮説も、いずれかの RQ で確かめるか、範囲外とした理由が書いてあるか）
   - `issue-tree.md` の葉と、RQ（優先度の高い葉が RQ になっているか）
   - `docs/study/pilot/results.md` で「答えられない」「保留」の仮説と、それに依存する RQ（保留のまま進める RQ は、概要にその旨があるか）
   - `premises.md` の RP3（範囲）と、RQ の「範囲」
   - `premises.md` の RP4（期限）・RP5（予算）と、RQ の数と `spec_order.md` の並び、`config.yaml` の `session.estimates`（期限内に終わる見込みか）
   - `premises.md` の RP6（使えるデータとアクセス）・RP9（倫理と個人情報）と、RQ の「手法」と「人の作業の見込み」（定性調査の RQ に、同意と倫理審査の `[人]` が見込まれているか）
   - `docs/method.md` と、`config.yaml` の `commands`、RQ の「手法」
   - 憲章と、`docs/quality.md`、`config.yaml` の `confidence.levels`・`sources.min_grade`
   - `000-research-foundation.md` と、`docs/method.md` の分析環境、`wide.md` の用語と定義
   - `999-research-report.md` と、`premises.md` の RP1（読み手）・RP8（成果物の形式）
   - `spec_order.md` の並び（`000` が先頭、`999` が最後）
   - `wide.md` で根拠に使うとした出典と、`sources/S000-*.md`（実在を確かめた方法と等級があるか）
3. `$RK handover --note "調査全体の工程（R1〜R12）を完了"` で引き継ぎ書を更新する。
4. §3 の形でコミットする（引き継ぎ書の更新を含める）。

## 5. 完了報告

R12 の後は、RQ の工程には進まずに止まる（`config.yaml` の `session.stop_after_bootstrap` が既定の `true` のとき。自動モードでも止まる）。調査全体の工程は検索が多く、RQ の工程は 1 件ごとに検索の予算を使うためである。

- 作成したファイルの一覧
- 調べたいことの原文、選んだ問いと調査の名前（仮題）、読み手、決めたいこと（D1〜）、期限
- 選んだ問いの立て方（型）と、選ばなかった案
- RP1〜RP12 の要約（未決のまま残した項目があれば、その一覧）
- イシューツリーの根と第 1 層、仮説（H1〜）の一覧と反証条件の要約
- 予備調査の結果（仮説ごとの判定。保留の仮説と、確かめる時期と方法。省いたときは理由）
- 採用した手法と分析環境、`commands` の埋まり具合
- 憲章の要点（出典の等級、確度の段階、倫理）
- RQ の数と、着手順の先頭 3 件、`000` と `999` の主な要求
- 品質基準の要点（根拠に使える最低の等級、確度の要求、レビューの合格条件）
- 出典の件数（等級別。`$RK sources list` で数える）
- 検証の結果（エラー、警告、`doctor` の WARN）
- 自動モード・一括質問モードのとき: `docs/auto-decisions.md` のうち、見直しの優先度が「高」の判断の一覧と、見直しに使うスキル（§7「記録」）
- 次の案内:
  - **新しいセッションを開いて**、`researchkit-all`（引数なし）で、`000-research-foundation` から 1 件ずつ、仕様・計画・収集・分析・主張のまとめ・5 軸レビューを通して進める。`researchkit-all all --auto` で無人で進めることもできる（検索の残りが足りなくなると、RQ の区切りで止まる。そのときは、また新しいセッションで同じコマンドを実行する）
  - 自動モード・一括質問モードのときは、先に `docs/auto-decisions.md` を見直す
  - 工程を分けたいときは、`researchkit-question`（設計の工程）と `researchkit-execute`（実行の工程）を使う
  - 有料資料の購入、アクセス権の申請、倫理審査など、人の作業が要るものがあれば、その一覧
  - 進捗と引き継ぎ書は `researchkit-status`

## 6. 規則と止まる場面

### 規則

- 各ステップの中身は、それぞれのスキルの SKILL.md に従う。このスキルで手順を省いたり、ヒアリングを飛ばしたりしない。自動モード・一括質問モードでは、ヒアリングや合意の手順を §7 の規則で置き換える（調査、出典の実在の確認、比較、予備調査、書き出し、検証は省かない）。
- ユーザーが「このステップは後でやる」と明示した場合は、そのステップを飛ばして次に進んでよい。完了報告に、飛ばしたステップと影響を書く。飛ばしたステップは記録しない（再実行時に再開の対象になる）。ただし R1（決めたいこと）、R5（仮説）、R8（憲章）、R9（RQ の一覧）は、後のステップがすべて前提にするので飛ばせない。飛ばしたいと言われたら、影響を示して確かめる。R6 を省く場合は §4「R6」の手順による（飛ばすのではなく、省いた判断を記録する）。
- R2 と R6 の調査は、AI が実行できるもの（Web 検索、公開データの所在の確認、試しの集計）を実際に行う。インタビューの試しなど人が行うものは `[人]` として計画を書き、「保留」にして、立ち上げは止めない。
- 応答と成果物は、プロジェクトの言語ルール（`.kiro/steering/language.md`）に従う。

### 止まる場面

次の場面では、モードを問わず止まる（対話モードではユーザーに確かめ、自動モード・一括質問モードでは止まった理由と判断してほしい事項〈選択肢と推奨案〉を報告して終了する）。判断した後にもう一度 `researchkit-bootstrap` を実行すれば（モードの指定は問わない）、続きのステップから再開する。

- R0 で、ブランチが `main`（クラウドセッションでは作業ブランチ）でない、または未コミットの変更がある
- R0 で、調べたいことの入力がなく、引数にもない（`--adopt` で既存の資料を入力として扱える場合を除く）
- R2・R6 の前の `$RK budget` が `VERDICT: STOP`
- `--adopt` の計画で、ユーザーが書いた資料を上書き・移動しないと進められない場合（§8）
- R6 で、同じ仮説が 2 回続けて「答えられない」になった（問いの立て方の見直しはユーザーが決める）
- R6 で、すべての仮説について主なデータ・文献が手に入らないと分かった（調査の範囲か手法の前提が崩れている）
- R4 以降で、RP9（倫理と個人情報）について、倫理審査や法的な判断が要ると分かり、それなしには手法を決められない
- R12 の検証エラー、または R9 の `validate.py` のエラーが、同じ原因で 3 回直しても 0 件にならない

## 7. 自動モード（`--auto`）と一括質問モード（`--oneshot`）

どちらのモードも、各ステップのスキルでユーザーに聞く論点（ヒアリング、案の選択、書き出し前の合意など）を、エージェント自身が作る推奨案で決めて進める。違いは、最初に一度だけ質問するかどうかである。

立ち上げで決めることは、読み手、決めたいこと、範囲、期限、予算、使えるデータなど、ユーザーしか知らない前提を多く含み、後のすべての RQ の土台になる。そのため、自動で決めたことは**仮定**として扱い、そうと分かる形で記録して、後から見直せるようにする（下の「記録」）。各スキルの「推測で埋めない」は、このモードに限り「推奨案を仮定として明示して採用し、記録する」に置き換える。ただし、**事実（文献、統計、数値）は自動モードでも推測で埋めない**。調べて出典を付けるか、「未調査」と書く。

### 一括質問（`--oneshot` の R0）

R0 の 1〜5 の後で、次の候補のうち、入力（`docs/concept/core-question.md`）と引数から決まらないものを上から順に最大 4 つ選び、AskUserQuestion の 1 回にまとめて質問する。各問には推奨案を先頭に `(Recommended)` 付きで置く。

| 順 | 論点 | 使うステップ |
|---|---|---|
| 1 | 読み手と、答えを使って決めたいこと（RP1、RP2） | R1、R3、R4、R5、R11 |
| 2 | 期限と、調査にかけられる手間・費用（有料の資料を買えるか）（RP4、RP5） | R3、R4、R6、R7、R9 |
| 3 | 範囲（地域、期間、対象）（RP3） | R2、R4、R5 |
| 4 | 使えるデータとアクセス（社内データ、有料データベース、インタビューできる相手）（RP6） | R3、R6、R7 |
| 5 | 要求する確度と、最終成果物の形式（報告書／スライド／メモ）（RP7、RP8） | R3、R8、R11 |
| 6 | インタビュー・アンケートなど人を対象にする調査を行うか、倫理審査の要否（RP9） | R4、R7、R8 |
| 7 | 利害関係（スポンサーの意向、結論に利害を持つ人）と、その開示（RP10） | R4、R8 |
| 8 | 調査と成果物の言語（RP11） | R2、R11 |

- 回答は `docs/concept/core-question.md` の末尾に「追記（YYYY-MM-DD、一括質問の回答）」の節として書き、`docs(bootstrap): 一括質問の回答を入力に追記` でコミットする（trailer は付けない）。入力に書くので、以降のスキルは回答を「確定」の根拠として使える。
- 再開したときに、この節がすでにあれば質問しない。
- 質問はこの 1 回だけにする。回答から新しい論点が出ても、以降は自動モードで決める。

### 各ステップでの自動の決め方

| ステップ | 論点 | 自動モードでの動作 |
|---|---|---|
| R0 | ブランチが `main`（クラウドセッションでは作業ブランチ）でない、未コミットの変更がある | 止まる（§6） |
| R0 | 入力がない | 引数に追記や希望以外のテキストがあれば、それを入力として `core-question.md` に書く。なければ止まる |
| R1 | 問いの言い換え案の選択、決めたいこと（D）の書き方 | 採点が最も高い案を採る（`researchkit-seed` の自動モード）。読み手と決めたいことが入力から分からなければ、推奨案を仮定として書き、見直しの優先度を「高」にする |
| R2 | 追加の調査観点 | 追加しない。Web を調べられない環境では「未調査」と書いて進め、見直しの優先度を「高」にする |
| R3 | 3 案からの選択 | 推奨案を採る。決定への効きが同じなら、期間と費用が小さい案を採る。型の選択は見直しの優先度を「高」にする |
| R4 | RP1〜RP12 の未決の項目 | 種・調査・問いの立て方から推奨案を作って採用し、状態を「確定」にする。質疑記録は `#### Q<n>（ラウンド 1, auto）— <項目 ID>` とし、回答の頭に `(auto: 仮定)` を付けて根拠を書く |
| R5 | イシューツリーの切り方、仮説の選び方 | 推奨案を採る。仮説は、外れたら決定が変わるものを先にする |
| R6 | 確かめ方、判定 | AI が実行できる方法を選んで実際に行い、結果で判定する。人が行う方法しかない仮説は「保留」にする |
| R7 | 手法の 3 案からの選択、分析環境 | `researchkit-method` の自動モードで決める。手法と有料のデータ源は見直しの優先度を「高」にする |
| R8 | 憲章の原則の確認 | `researchkit-constitution` の自動モードで決める。批准日など不明な日付は実行日にする |
| R9 | 分割案の合意、着手順 | 提示せずに書き出す。着手順は、決定への効きが大きく、ほかの RQ の前提になるものを先にする。分割案は完了報告に載せる |
| R10 | 共通基盤の範囲、書き出しの合意 | 各 RQ の想定する情報源と手法から必要と判断できるものを入れる |
| R11 | 品質の水準、最終成果物の形式、書き出しの合意 | RP7・RP8 から推奨値を採る。根拠に使える最低の等級は既定（`C`）より下げない |
| R12 | 整合の食い違い | 該当するスキルの更新モードの手順で、推奨の修正を当てる |

### 記録

- 自動で決めたことは、すべて `docs/auto-decisions.md`（様式: [templates/auto-decisions.md](./templates/auto-decisions.md)）に追記する。ステップごとに節を分け、1 件ごとに次を書く。
  - 論点、採用した案、ほかの選択肢、理由
  - 根拠の種類（入力 / 一括質問の回答 / 調査 / 予備調査 / 推測）
  - 見直しの優先度（高 / 中 / 低）。読み手、決めたいこと、範囲、期限、予算、問いの立て方の型、手法、倫理と個人情報、利害関係、根拠が推測だけのものは「高」にする
  - 反映したファイルと、見直すときに使うスキル（例: `researchkit-sparring`、`researchkit-hypothesis` の更新モード、`researchkit-method` の更新モード）
- 各ステップのコミットに `docs/auto-decisions.md` の更新を含める。
- サブエージェントに調査などを任せたときは、記録すべき判断をサブエージェントの最終回答で返させ、記録は親が行う（steering「サブエージェントに任せるとき」）。

## 8. 取り込みモード（`--adopt`）

既存の調査（企画書や調査メモ、途中まで進めた報告書、文献リスト、集めたデータ、インタビューの記録がある調査）に researchkit を入れたときに、すでにある資料を researchkit の成果物に移し替えて、RQ の工程（`researchkit-all`）に入れる状態にする。**元の資料は動かさない・消さない・書き換えない。** 移し替えた成果物の冒頭には、出典の元ファイル（パスと、読んだ時点のコミット）を書く。

### 8.1 資料を探す

資料の場所は調査ごとに違うので、決め打ちせずに探す。

1. `git ls-files`（Git でなければ `find`）と、`docs/`・`research/`・`notes/`・`data/`・`literature/`・ルートの `*.md` を一覧し、見出しと冒頭を読む。`.researchkit/config.yaml` の `paths` をすでに合わせてあれば、それを手がかりにする。大きなデータファイル、PDF の本文、仮想環境（`.venv/`、`renv/`）、キャッシュは中身を読まない（名前と大きさだけを見る）。
2. 各ファイルを、§2 のステップの成果物の候補に当てる。目安は次のとおり。

   | ステップ | 候補になる資料の例 |
   |---|---|
   | R1 | 企画書、調査の依頼書、提案書（proposal）、キックオフのメモ、`README.md` の目的 |
   | R2 | 先行調査のメモ、文献リスト（`*.bib`、`references.md`、文献管理ソフトの書き出し）、リンク集、競合の一覧 |
   | R3〜R4 | 調査の設計のメモ、要件の合意、スコープの文書、制約の一覧 |
   | R5 | 仮説の一覧、論点の整理、イシューツリー、ロジックツリー |
   | R6 | 試しの検索、パイロット調査、試しのインタビューの記録 |
   | R7 | 分析のコード（`*.py`、`*.R`、`*.ipynb`）、環境の定義（`pyproject.toml`、`requirements.txt`、`renv.lock`）、調査票 |
   | R8 | 既存の調査の規程、倫理審査の申請書、引用の規則 |
   | R9〜R11 | 問いの一覧、目次案、作業計画、報告書の下書き、途中の分析結果 |

3. 1 つの資料が複数のステップにまたがってよい（例: 1 本の企画書から R1 と R4 を作る）。
4. 既存の出典（文献リスト、URL の一覧）とデータは、§8.2 の規則で出典台帳とデータの目録に対応づける。ファイルは動かさない。

### 8.2 計画を作る

ステップごとに、次の 4 つのどれにするかを決め、根拠（候補の資料と、足りないもの）を付けて一覧にする。

| 扱い | 条件 | 動作 |
|---|---|---|
| 移し替える | 既存の資料に中身があり、researchkit の様式（テンプレートの見出しと表）にない | そのステップのスキルの更新モード（取り込み）で、資料を入力にして成果物を作る。資料に書いてあることは質問し直さず、足りない項目だけを質問（自動モードでは推奨案）で埋める |
| 完了として記録 | 既存の資料がすでに researchkit の成果物の場所と様式に合っている | 内容を確かめ、変更せずに §3 の形で記録する |
| 新しく作る | 候補の資料がない | そのステップのスキルを通常どおり実行する |
| 飛ばす | 調査が進んでいて、作っても後の工程で使わない（例: 問いが確定している調査の R3 の 3 案、収集を終えた調査の R6） | 記録せず、理由を完了報告に書く。R1・R5・R8・R9 は飛ばせない（§6） |

既存の資料を尊重する規則:

- **出典（R2）**: 既存の文献リストやリンク集は、そのまま根拠にしない。根拠に使うものだけを `sources/S000-*.md` に登録し、そのときに 1 件ずつ実在を確かめる（steering の基本原則 2）。確かめられなかったものは等級 `D` にする。元のリストは動かさず、`wide.md` から参照する。
- **データ**: 既存のデータは動かさない。`paths.data` を既存の置き場所に向けるか、`data/manifest.md`（R10 で形式を決める）に既存のパスのまま載せるかを、計画に書いて合意を取る。個人情報を含むデータは、中身を出力せず、`[人]` の確認の対象にする。
- **問い（R9〜R11）**: 既存の問いの一覧や目次案があれば、問いの切り方と順番を尊重する。予約番号の `000`・`999` が別の名前で使われていれば、その名前のまま共通基盤・統合報告として扱い、新しく作らない。
- **進んだ調査**: 収集や分析を終えた問いは、仕様を作り直さない。`docs/questions/` の概要だけを作り、状態と、後から `researchkit-findings` で主張の表に移し替えることを次の案内に書く。
- **既存の判断**: 既存の資料で決まっていること（手法、データ源、範囲、確度の言い方）は、researchkit の推奨と違っても既存を採る。変えた方がよい点は、`docs/auto-decisions.md`（対話モードでは完了報告）に「見直しの候補」として書くだけにし、勝手に変えない。
- **パス**: 既存の配置に合わせて `.researchkit/config.yaml` の `paths` を書き換えてよい（例: 出典のメモが `refs/` なら、そのまま残し、`sources/` は新しく作る）。合わせた後に `$RK init` を実行し、足りないディレクトリだけを作る。

### 8.3 合意と実行

- **対話モード**: 計画の一覧をユーザーに示し、AskUserQuestion で確かめる（ステップの数が多いので、扱いを変えたいステップだけを答えてもらう形でよい。推奨は一覧のとおり）。合意した計画を `docs/adopt-plan.md`（様式: [templates/adopt-plan.md](./templates/adopt-plan.md)）に書き、`docs(bootstrap): 取り込みの計画を作成` でコミットする（trailer なし）。
- **自動モード・一括質問モード**: 計画の推奨案をそのまま採り、`docs/adopt-plan.md` と `docs/auto-decisions.md` に記録する（「完了として記録」「飛ばす」にしたステップは、見直しの優先度を「中」にする）。
- 計画のあとは、§3 の再開の規則で R1 から順に進む。「完了として記録」のステップは内容を確かめて記録だけを作り、「飛ばす」のステップは記録しない。再開したときに `docs/adopt-plan.md` があれば、計画を作り直さずにそれに従う。
- R12 の検証で、既存の資料を書き換えないと直せないエラーは、一覧と直し方の案を完了報告に挙げ、ユーザーの合意を得てから直す（自動モードでは直さずに止まる）。

### 8.4 完了報告に足すもの

- ステップごとの扱い（移し替えた / 完了として記録した / 新しく作った / 飛ばした）と、移し替えた元の資料
- 出典台帳に登録した件数と、確かめられなかった（等級 `D`）件数
- データの扱い（`paths` を向けた / 目録に載せた）と、個人情報の確認が要るもの
- 既存の判断で、researchkit の推奨と違うまま残したもの（見直しの候補）
- 収集や分析を終えた問いと、主張の表に移し替えるための案内
