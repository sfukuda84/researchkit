# researchkit-analyze スキル（Q7: 整合性の検証 ×2）

集めた後に直すより、集める前に直す方が安い。収集の前に、仕様・計画・タスクの間の矛盾と漏れを取り除く。とくに、**答えの形に答える分析がない**、**仮説を捨てる条件が観測できない**、**反対の証拠を探す作業がない**の 3 つは、収集の後では取り返しにくい。

ステップ番号、モード、質問の規則は [`researchkit-worktree`](../researchkit-worktree/SKILL.md) に従う。通常は [`researchkit-question`](../researchkit-question/SKILL.md) か [`researchkit-all`](../researchkit-all/SKILL.md) から呼ばれる。チェックポイント（Q7-1・Q7-2）は呼び出した統括スキルが記録する。単独で実行したときは、最後に `$HELPER checkpoint <RQ_NAME> Q7-1 "<『ステップ番号』の節の subject>"`（2 回目は Q7-2）を記録する。パスは `.researchkit/config.yaml` の `paths` で読み替える。

## 1. 対象と入力

- 対象: `studies/<RQ_NAME>/`（以下 `RQ_DIR`）の `spec.md`、`plan.md`、`tasks.md`。どれかがなければ、欠けている工程（`researchkit-specify`、`researchkit-plan`、`researchkit-tasks`）を案内して止まる。
- 照合の相手:
  - 憲章 `.researchkit/memory/constitution.md`（出典の等級、確度の段階、引用、数値、倫理、AI 利用の開示）と品質基準 `docs/quality.md`（出典の最低等級、確度の要求、再現性、レビューの合格条件）
  - RQ の概要 `docs/questions/<RQ_NAME>.md`、問いの種 `docs/concept/seed.md`（`D`）、前提 `premises.md`（`RP`）
  - 仮説 `docs/study/hypotheses.md`（`H` と反証条件）、イシューツリー `issue-tree.md`（`I`）
  - 手法 `docs/method.md` と、`plan.md` で選んだ手法の参照文書 `researchkit-method/references/`
  - 用語集 `docs/glossary.md`、依存する RQ の `findings.md`、`.researchkit/config.yaml`（`sources.min_grade`、`confidence.levels`、`session.estimates`、`commands.analysis`）

`--round` の指定がなければ、`$HELPER state <RQ_NAME> --phase design` の `NEXT_STEP`（Q7-1 なら 1 回目、Q7-2 なら 2 回目）に合わせる。

## 2. 重大度

| 重大度 | 基準 |
|---|---|
| CRITICAL | 憲章・品質基準の MUST に反する（最低等級より低い出典だけで答える計画、確度の要求を満たせない計画、同意・匿名化の手当てのない定性調査、利用規約に反するデータの使い方）。どの決定 `D` にもつながらない（000・999 を除く）。判定の基準 `AC` に答える分析が計画にない。仮説の反証条件が計画にない、または観測できない |
| HIGH | 答えの形と分析の出力が合わない（比較表が要るのに数値 1 つを出す計画）。判定の基準・反証条件・反対の証拠の探し方に対応するタスクがない。反対の証拠を探す計画がない。範囲（地域・期間・母集団）と情報源・標本が食い違う。結果を見てから決めることが分析の計画に残っている。人が行うべき作業に `[人]` がない、または AI ができる作業に `[人]` がある。`[人]` のタスクに完了の確かめ方がない |
| MEDIUM | 用語の揺れ（spec・plan・tasks・用語集で同じものを違う名前で呼ぶ、操作的定義と違う数え方）。単位・時点・粒度の食い違い。タスクの依存の順の誤り（取得の前に分析がある）。検索数の見積もりが `session.estimates` を大きく超えるのに対処がない。確度の付け方の段階名が憲章と違う。出典 ID の範囲の割り当てがない（並行に集めるのに） |
| LOW | 表記の細部、必須でない欄の書き漏れ、より良い言い回し |

未完了の `[人]` のタスクは、漏れや不整合として扱わない（steering の「人が行うタスク」）。

## 3. 検出の観点

各回、次の観点で 3 つのファイルと照合の相手を読む。観点の記号は所見の ID の頭に使う。

| 記号 | 観点 | 見ること |
|---|---|---|
| A | 憲章と品質基準 | 計画の出典の等級、確度の付け方、再現性（スクリプトと `commands.analysis`）、引用、倫理、AI 利用の開示が、MUST を満たすか。憲章との矛盾は常に CRITICAL である。原則の解釈を緩めて合わせない |
| B | 決定と仮説のつながり | spec の `D` が `seed.md` にあり、答えと決定の分かれ目があるか。spec の `H` が `hypotheses.md` にあり、計画に支持・反証の条件があるか。反証条件が、計画のデータと指標で観測できるか。RQ の概要の決定・仮説と一致するか |
| C | 答えの形と分析 | 小問 `SQ` ごとの答えの型・単位・粒度に、計画の分析と出力（`analysis/out/` のキー）が合っているか。因果を問う小問で、手法の確度の上限が要求に届くか |
| D | カバレッジ | `AC` ごとに分析とまとめのタスクがあるか。計画の情報源・データ・反証条件・反対の証拠の探し方の各行にタスクがあるか。どこにも対応しないタスクがないか |
| E | 範囲と標本 | 計画の情報源・期間・地域・標本が、spec の範囲と範囲外に合っているか。母集団から一般化する範囲が、標本の取り方で言えるか |
| F | 用語と単位 | spec の用語の操作的定義、用語集、計画の数え方、タスクの表現が一致するか。通貨・名目と実質・為替・税・分母が一貫しているか |
| G | バイアスへの備え | 反対の証拠を探す検索があるか。検索語が仮説に有利な語だけでないか。包含・除外の基準が結果を見る前に決まっているか。分析の分岐が先に決まっているか。スポンサーの利害が前提にあるなら、その扱いがあるか |
| H | 実現性 | 検索数の見積もりと `session.estimates`。有料の資料・アクセス権・同意が `[人]` になっているか。依存する RQ の答えが手に入るか。手法が `docs/method.md` の範囲か |
| I | タスクの書式と順序 | 書式（ID、パス、完了の確かめ方）、`[P]` の正しさ、依存の順、`[人]` の付け方（steering の規則） |

**000 と 999**: `000-research-foundation` では、観点 B（決定と仮説）と G（バイアス）は対象外とし、C・D を「基盤ごとの完成条件に、整える作業と確かめる作業があるか」として読む。主張を作るタスクがあれば HIGH とする。`999-research-report` では、B を「すべての `D` に結論の章があるか」、C を「`999-research-report.md` の読み手・形式・構成に計画が合うか」、D を「すべての RQ の主張が取り込まれるか、採らない理由があるか」、H を「ほかの RQ がすべて `完了` か `人の作業待ち` か」として読み、新しい収集のタスクがあれば HIGH とする。

## 4. 手順（各回に共通）

1. §1 の入力を読む。全文を一度に読まず、各ファイルから要る節（spec の小問・答えの形・判定の基準・範囲・用語、plan の各節の表、tasks のタスクの行）を抜き出して内部の対応表を作る。
   - 判定の基準 `AC`、仮説 `H`、計画の情報源・データ・分析の各行の一覧と、それぞれに対応するタスク ID
   - 用語の一覧（spec・用語集・plan・tasks での呼び方）
2. §3 の観点で検出する。所見は具体的な箇所（ファイルと節、行）を挙げて書く。存在しない節を推測で補わない。所見は多くて 50 件にし、それを超える分は件数だけまとめる。
3. 検出結果を §5 の様式で表にする。
4. 直し方を決める。
   - 直し方が 1 つに決まるものは直す。
   - 判断が要るものは、推奨案（`**Recommended:**`）を添えて質問する（通常モード）。自動モードでは推奨案を当て、`RQ_DIR/auto-decisions.md` に記録する。
   - 仕様を直したときは、`spec.md` の `## Clarifications` に `### Session YYYY-MM-DD (analyze)` として記録する。収集の前なので、計画は本文を直してよい（「計画の変更」の表は要らない）。
   - **憲章・品質基準・`docs/method.md` の改訂が要るときは、直さずに報告する**（自動モードでは止まる）。仮説そのものを変える必要があるときは、`hypotheses.md` を直し、RQ の概要にも反映する（基本原則 10）。
5. 修正を当てる。RQ の概要（`docs/questions/<RQ_NAME>.md`）や用語集を直したときは、`python3 <skills>/researchkit-questions/scripts/validate.py` を実行し、エラーを 0 件にする（引数は `researchkit-questions` の SKILL.md に従う）。
6. 検出結果と修正を `RQ_DIR/reviews/analyze-<回>.md` に保存する。同じ回をやり直したときは、前の結果を消さずに、日付つきの節を足す。
7. 指摘が 0 件で変更がなくても、記録を残す（チェックポイントは統括スキルが記録する）。

## 5. 各回の進め方

### Q7-1（検出と修正）

§3 のすべての観点で検出し、CRITICAL・HIGH・MEDIUM をすべて直す。LOW は直してもよいし、残してもよい。

カバレッジの表（`AC` と `H`、計画の各行 → タスク ID）を作り、対応のない行を 0 件にする。

### Q7-2（確認）

1 回目の修正を当てた後の 3 つのファイルを、**1 回目の所見を見ずに**もう一度 §3 のすべての観点で読む。1 回目の修正が新しい矛盾（用語の揺れ、ID のずれ、依存の順の崩れ）を生んでいないかを特に見る。その後で 1 回目の所見と突き合わせ、すべて解消していることを確かめる。

次をすべて満たすことを確かめる。満たさなければ直してから記録する。

- CRITICAL・HIGH・MEDIUM が 0 件
- 憲章・品質基準の違反が 0 件
- `AC`、`H` の反証条件、計画の情報源・データ・分析・反対の証拠の探し方の各行に対応するタスクのカバレッジが 100%
- `validate.py` を実行した場合は、そのエラーが 0 件

LOW は、直さずに残してよい（一覧を報告する）。

## 7. 完了報告

- 回ごとの所見の件数（重大度別）と、直したもの
- 質問して決めたこと（自動モードでは採用した推奨案）
- カバレッジ（2 回目の時点で 100% か）
- 憲章・品質基準・`docs/method.md` の改訂が要るとして報告した事項（あれば）
- 記録のパス（`RQ_DIR/reviews/analyze-<回>.md`）
- 次の案内: 1 回目の後は `researchkit-analyze <RQ_NAME> --round 2`（Q7-2）。2 回目の後は、統括スキルの Q13（`researchkit-question` のとき）か、収集 `researchkit-execute <RQ_NAME>`（Q8）
