# researchkit-seed スキル（R1: 問いの種 → 決めたいことと問い）

ユーザーの 1 文を、以降の調査と問いの立て方の検討に使える形にする。調査は「知りたい」から始めると、答えても何も決まらない調査になりやすい。そこで最初に、**誰が何を決めるために答えを使うのか**を書く（steering の基本原則 3）。まだ調べない。**入力の 1 文は一字も変えずに残す。**

パスは `.researchkit/config.yaml` の `paths` で読み替える。進捗の記録とモードは [`researchkit-bootstrap`](../researchkit-bootstrap/SKILL.md) の §3・§7 に従う。

## 1. 引数

```text
$ARGUMENTS
```

- `--auto` を取り除いた残りを、問いの種の 1 文として扱う。
- 引数がなければ、`docs/concept/core-question.md` を種として読む。それもなく、`seed.md` もなければ、次のように聞く（自動モードでは止まる）。

  > 調べたいことを 1 文で教えてください。「〇〇は△△か」という問いの形でも、「〇〇の市場に参入すべきか判断したい」という決めたいことの形でも、テーマの名前だけでも構いません。誰がその答えを使うか、いつまでに要るかが決まっていれば、それも添えてください。

- `seed.md` がすでにあれば、原文を残したまま「追記（YYYY-MM-DD）」の節を足す（更新モード）。決めたいこと（D）を変えたときは、ID を振り直さない（消した D は「取り下げ」と書いて残す）。後の工程（`docs/questions/` の「つながる決定」）が ID を参照しているためである。
- 既存の調査に取り込んだとき（企画書、依頼書、提案書がある）は、それを読み、書いてあることを「要素」と「決めたいこと」に写して出典（パスと節）を書く。質問し直さない。

## 2. 手順

1. **原文を記録する。** 種の 1 文を、そのまま `seed.md` の「原文」に書く。
2. **要素を分ける。** 原文と `core-question.md` の追記（一括質問の回答を含む）から読み取れることを、次の表に分ける。読み取れないものは「未定」と書き、推測で埋めない。

   | 要素 | 内容 |
   |---|---|
   | 調べたいこと（テーマ） | 何について知りたいか |
   | 読み手 | 答えを読む人、使う人（経営層、事業の担当、研究室、行政の担当、自分） |
   | 決めたいことの手がかり | 答えを使って何を決めるか（参入、投資、方針、設計、論文の主張） |
   | 期限の手がかり | いつまでに答えが要るか。その日付を決める出来事（会議、締め切り） |
   | 範囲の手がかり | 地域、期間、対象（業界、年齢層、製品） |
   | 手法の手がかり | 文献、統計、自社のデータ、インタビューなどの言及 |
   | すでに分かっていること | 依頼者が知っている事実や、過去の調査 |

3. **読み手と答えの使い道を書く。** 読み手ごとに、答えを受け取って何をするか（会議で決める、計画を書き直す、論文に書く、公開する）を 1 行で書く。読み手が複数なら、主な読み手を 1 人（1 つの立場）に決める候補を示す（決まらなければ「未定（R4 の RP1 で決める）」）。
4. **決めたいことを D1〜 で書く。** 各決定について、次を書く。決定が読み取れない種（純粋な好奇心、学術の問い）でも、「答えを何に使うか」を決定として書く（例: 「D1: 論文の第 3 章で〇〇を主張するかどうか」）。

   | 項目 | 内容 |
   |---|---|
   | 決めること | 選ぶ・選ばない、どれを選ぶか、いくらにするか |
   | 決める人 | 読み手のうち、誰が決めるか |
   | 期限 | いつまでに決めるか |
   | 選択肢 | 今見えている選択肢（2〜4 個。「何もしない」も含める） |
   | 今の見込み | 調査をしなければ、どれを選びそうか |

   決定は 1〜5 個に絞る。5 個を超えたら、まとめるか、主な決定と従の決定に分ける。
5. **「何が分かれば何を決められるか」を書く。** 決定ごとに、決め方の規則を「〇〇が△△なら選択肢 A、そうでなければ B」の形で書く。ここが調査の中心になる。
   - 規則の左辺（〇〇）が、調べて答える対象である。数値なら、決定が分かれる境目（しきい値）の見当を書く（例: 「市場が年 100 億円以上なら参入を検討する」）。
   - 答えがどちらに出ても選ぶ選択肢が同じなら、その〇〇は調べても決定を変えない。表に「決定を変えない」と書き、問いの候補から外す（Douglas W. Hubbard『How to Measure Anything』の「情報の価値」〈value of information〉の考え方。外れたときの損失が大きく、今の見込みが不確かなものほど調べる価値が高い）。
   - 外れたときの損失（間違った選択肢を選んだときに何を失うか）を 1 行で書く。調べる優先度の材料にする。
6. **問いに言い換える。** 原文を、調査で答える問いの形に 3 通り言い換える。
   - 案 A: 原文に忠実な問い
   - 案 B: 決定に寄せた問い（5 の規則の左辺をそのまま問いにする）
   - 案 C: 範囲・対象・期間のどれかを絞るか広げた問い

   問いは疑問文で書き、答えの形（はい・いいえ、数値、一覧、比較、理由の説明）が分かるようにする。
7. **4 条件で採点する。** 各案を次の 4 条件で ◎／○／△ に評価し、弱い条件をどう強くするかを 1 行で添える。

   | 条件 | 見るもの |
   |---|---|
   | 決定につながる | 答えが出たら、D のどれかで選ぶ選択肢が変わりうるか |
   | 答えの形が見える | 何が書かれていれば「答えた」と言えるかが分かるか（数値、はい・いいえ、比較の表など） |
   | 範囲が見える | 地域、期間、対象、用語の意味が、少なくとも読み手と話が通じる程度に決まっているか |
   | 期限内に答えられる | 期限と手間の見込みで、公開の情報や手に入るデータから答えが出せそうか（R6 の予備調査で確かめる） |

8. **調査の論点を挙げる。** R2（予備調査・広域）で調べるべきことを 5〜10 個挙げる。既存の調査やレポートの有無、先行研究の系統、公的統計やデータの所在、用語の定義の揺れ、論点と立場の対立など。決め方の規則の左辺に関わるものを先に置く。
9. `seed.md` を書き、ユーザーに示す。

### 対話モード

- 読み手と決めたいことが要素から読み取れなかった場合は、問いの選択の前に聞く（AskUserQuestion。1 回に 4 問まで）。推奨案を先頭に `(Recommended)` 付きで置く。調べたいことだけがあり、決めたいことがないと言われたら、「答えを何に使うか」（社内で共有する、記事にする、自分の判断の材料にする）を選択肢にして聞く。
- 3 案のうち、どれを調査の軸にするかを質問する。1 つに絞らず「全部を材料に調べる」も選べる。推奨案を先頭に `(Recommended)` 付きで置く。
- 回答を `seed.md` の「選択」に書く。

### 自動モード

- 読み手と決めたいことが入力から分からなければ、推奨案を `(auto: 仮定)` と明示して書き、`docs/auto-decisions.md` に見直しの優先度「高」で記録する。決めたいことは、入力の言い回しから最も自然なもの 1〜2 個にとどめる。
- 採点が最も高い案を調査の軸にし、`docs/auto-decisions.md` に記録する（見直しの優先度: 中）。同点なら案 B（決定に寄せた問い）を採る。`seed.md` の「選択」には、`(auto)` と理由を書く（例: 「調査の軸: B（auto）。理由: 採点が最も高く、D1 に直接つながる」）。

## 3. 出力

`docs/concept/seed.md`（様式: [templates/seed.md](./templates/seed.md)）

調査の名前（仮題）を決めたら、`.researchkit/config.yaml` の `title` が空なら書く。終わったら `researchkit-bootstrap` §3 の形で `R1` を記録する（単独で実行したときも記録する）。

## 4. 完了報告

- 原文、読み手、決めたいこと（D1〜）と期限
- 決め方の規則（「何が分かれば何を決められるか」）の要約と、「決定を変えない」として外した論点
- 選んだ問いと仮題
- 調査の論点
- 次の案内: `researchkit-scan`（R2）

## 5. 規則

- 原文は一字も変えない。
- 決めたいことのない問いを、そのまま調査の軸にしない。決定が見つからなければ「答えの使い道」を決定として書く。
- 事実（市場の大きさ、先行研究の有無など）をこの段階で書かない。書きたくなったものは「調査の論点」に回す。
- 応答と成果物は、プロジェクトの言語ルール（`.kiro/steering/language.md`）に従う。
