# researchkit-clarify スキル（Q3・Q4: 仕様の明確化 ×2）

収集を始めてから「この語はどこまで含むのか」「いつ時点の数か」で迷うと、集めた資料が使えなくなる。明確化は、その迷いを収集の前に問いの仕様の段階で解消する。曖昧さは推測で埋めず、推奨案を添えて質問し、決まったことを仕様に書き戻す（基本原則 11）。

ステップ番号、モード、質問の規則は [`researchkit-worktree`](../researchkit-worktree/SKILL.md) に従う。通常は [`researchkit-question`](../researchkit-question/SKILL.md) か [`researchkit-all`](../researchkit-all/SKILL.md) から呼ばれる。チェックポイント（Q3・Q4）は呼び出した統括スキルが記録する。単独で実行したときは、最後に `$HELPER checkpoint <RQ_NAME> Q3 "<『ステップ番号』の節の subject>"`（2 回目は Q4）を記録する。パスは `.researchkit/config.yaml` の `paths` で読み替える。

## 1. 対象と入力

- 対象: `studies/<RQ_NAME>/spec.md`（以下 `RQ_DIR/spec.md`）。なければ `researchkit-specify` を案内して止まる（ここでは仕様を新しく作らない）。
- 参照: `docs/questions/<RQ_NAME>.md`、`docs/concept/seed.md`、`premises.md`、`docs/study/hypotheses.md`、`issue-tree.md`、`docs/scan/wide.md`、`docs/study/pilot/`、`docs/glossary.md`、憲章、`docs/quality.md`、依存する RQ の `findings.md`

`--round` の指定がなければ、`$HELPER state <RQ_NAME> --phase design` の `NEXT_STEP`（Q3 なら 1 回目、Q4 なら 2 回目）に合わせる。単独で呼ばれて判断できなければ、`## Clarifications` に Round 1 の記録がなければ 1 回目、あれば 2 回目とする。

## 2. 観点

各回、次の観点ごとに仕様を読み、`明確`／`一部`／`欠落` を内部で判定する。`一部` と `欠落` が質問の候補である。ただし、答えても収集・分析・判定の仕方が変わらないもの、手法や検索式・タスクの分け方に関するもの（Q5・Q6 で決める）は質問にしない。

### 1 回目（Q3）: 一般の曖昧さ

| 観点 | 見ること |
|---|---|
| 問いの範囲 | 問いと小問の境目。小問が多すぎる、重なる、問いの一部を担う小問がない |
| 決定とのつながり | 答えと決定の分かれ目が書けているか。分かれ目のしきい値（「〜以上なら」）が決まっているか |
| 答えの形 | 小問ごとの型が決定に合っているか（比較表が要るのに数値 1 つになっていないか）。求める確度は品質基準を満たすか |
| 判定の基準 | 答えが出た条件、答えが出ない条件、探すのを止める条件が、観測できる形か |
| 範囲外 | 読み手が含むと思いそうなものが、範囲か範囲外のどちらかに明記されているか |
| 読み手と期限 | 誰がいつ使う答えか。期限に間に合う範囲の問いか |
| 依存 | 依存する RQ の答えのうち、どれを前提に使うか。まだ答えが出ていない依存はないか |
| 倫理と権利 | 個人に関わるデータ、インタビュー、有料のデータベース、秘密情報を使う見込みがあるか |
| 曖昧な語と残った印 | 「主要な」「大手の」「最近の」「多くの」などの数の基準のない形容。`[NEEDS CLARIFICATION]`、`<…>` のプレースホルダ、TODO |

### 2 回目（Q4）: 調査特有の曖昧さ

1 回目の決定を前提に、一段細かく、**集めたものを数えるときに迷う点**を洗い出す。

| 観点 | 見ること | 推奨の例 |
|---|---|---|
| 用語の操作的定義 | 問いの中の語を、何をどう数えればそれに当たるか。境界の事例（含むか、含まないか）が決まっているか | 「利用者 = 直近 30 日に 1 回以上ログインした個人」。公的統計の定義があればそれに合わせる |
| 母集団 | 誰・どの企業・どの文献の集合について答えるか。標本から一般化してよい範囲 | 「国内で提供中の全サービス」。網羅できないなら「上位 N 社」と明記する |
| 期間と時点 | データの期間、答えの時点、年度と暦年、ストック（時点の量）とフロー（期間の量） | 暦年。最新の確定値の年を答えの時点にする |
| 地域 | 国、地域、言語圏。国内の一部か全体か。海外の資料をどこまで使うか | 前提 `RP` の範囲。海外の資料は比較の参考に限る |
| 比較の対象 | 何と比べて「大きい」「伸びた」と言うか。基準の年、基準の集団、競合の選び方 | 前年比と 5 年前比を並べる。競合は公開の資料で利用者数の上位から選ぶ |
| 単位 | 通貨、名目か実質か、為替の換算（どの日・どの平均の率か）、税込みか税抜きか、人・世帯・事業所の別、割合の分母 | 円、名目、税抜き。外貨は年平均の為替で換算し、換算の出典を記録する |
| データの粒度 | 年・四半期・月、全体・業種別・規模別、個人・世帯、企業・事業部。答えに要る粒度と、手に入る粒度の差 | 答えに要る最も粗い粒度に合わせる。細かい粒度は手に入れば内訳として示す |

定性調査を含む RQ では、母集団を「対象者の条件と選び方」、粒度を「発言・テーマ・類型」の単位として読む。文献レビューを含む RQ では、母集団を「対象とする研究の範囲（研究デザイン、対象者、発行年、言語）」として読む。

**000 と 999**: `000-research-foundation` では、決定とのつながりと判定の「答えが出ない条件」は見ない。2 回目は、用語集に入れる語の範囲、データの目録の粒度（何を 1 件とするか）、出典の等級の付け方の境界の事例に絞る。`999-research-report` では、2 回目の観点を、各 RQ の間で用語・単位・時点・母集団が食い違っていないか（統合したときに足し合わせられるか）として読む。

## 3. 質問の進め方

1. 候補の論点を、影響の大きさ × 不確かさの順に並べ、**各回最大 5 問**に絞る。同じ観点に偏らず、影響の大きい観点から先に聞く。
2. **1 問ずつ**示す。各問いは次の形にする。
   - `**質問:**` に、それだけで意味の通る疑問文（「〜ですか？」で終わる）を書く。見出しや ID だけを質問にしない。
   - 次の 1 文で、なぜ決める必要があるか（決まらないと収集・判定で何に困るか）を書く。
   - 選択式なら、推奨案を先に `**Recommended:** 案 <X> — <理由 1〜2 文>` で示し、選択肢（2〜5 個）を表にする。推奨の根拠には、前提 `RP`、品質基準、公的統計や先行研究の定義の慣例、予備調査の結果、手に入るデータの粒度を使う。
   - 短答式なら、`**Suggested:** <案> — <理由>` を示す。
   - ユーザーは、案の記号、「推奨どおり」、自分の短い答えのどれかで答えられる。
3. 回答があいまいなら、同じ問いの中で確かめる（問いの数に数えない）。
4. 重要な曖昧さが早く解消したとき、ユーザーが「もう十分」と伝えたとき、5 問に達したときは止める。先の問いを前もって見せない。
5. 質問すべき論点がなければ、「明確化が要る重要な曖昧さはない」と報告し、観点ごとの判定を短い表で示す。

`AskUserQuestion` が使える環境では、それで 1 問ずつ聞く。使えない環境では、同じ形を文章で示して回答を待つ。

**自動モード**では質問しない。各論点で推奨案を回答として採用する。推奨案を 1 つに絞れない論点は、範囲が狭く後から広げやすい案を採る（例: 地域を国内に限る、期間を短くする）。採った案は、行末に `(auto)` を付けて記録し、`RQ_DIR/auto-decisions.md` にも、ステップ、論点、選択肢、採用した案、理由、反映した節を書く。

## 4. 仕様への書き戻し

回答を 1 つ受け入れるたびに、次を行ってファイルを保存する（文脈が途切れても失わないため）。

1. `## Clarifications` の下の `### Session YYYY-MM-DD (Round 1)`（2 回目は `(Round 2)`、自動モードでは `(Round 1, auto)`）に、`- Q: <質問> → A: <回答>` を 1 行足す。
2. 本文の該当の節に反映する。

   | 決まったこと | 反映する節 |
   |---|---|
   | 小問の分け方、問いの言い回し | 問い・小問 |
   | 決定の分かれ目のしきい値 | つながる決定 |
   | 型、単位、粒度、時点、確度 | 答えの形 |
   | 答えが出た・出ない・止める条件 | 判定の基準 |
   | 対象、地域、期間、母集団 | 範囲・範囲外 |
   | 操作的定義、境界の事例 | 用語（ほかの RQ でも使う語は `docs/glossary.md` にも足す） |
   | 有料資料、個人データ、同意の見込み | 人の作業の見込み |

3. 回答で古くなった記述は、残さずに置き換える。仕様の中で矛盾する記述が残らないようにする。用語を統一したら、仕様全体で同じ語を使う。
4. 回答で解消した `[NEEDS CLARIFICATION]` を消す。
5. RQ の概要 `docs/questions/<RQ_NAME>.md` と食い違う決定になったら、概要の側も直す。

すべての質問を終えたら、`researchkit-specify` の「仕様の点検」の項目で仕様を見直す。

## 5. 完了報告

- 回（1 回目・2 回目）、質問した数と答えた数
- 更新した節の一覧
- 観点ごとの判定の表（`解消`: 一部・欠落だったが決めた、`保留`: 問いの数を超えた、または Q5 以降で決める、`明確`: もとから十分、`残り`: 一部・欠落だが影響が小さい）
- `保留` と `残り` があれば、その扱い（Q4 で扱う、Q5 の計画で決める、そのまま進めてよい）
- 仕様の点検の結果
- 次の案内: 1 回目の後は `researchkit-clarify <RQ_NAME> --round 2`（Q4）、2 回目の後は `researchkit-plan <RQ_NAME>`（Q5）
