# データ分析の進め方

`researchkit-method` が手法と分析環境を選ぶとき、各 RQ の `plan.md`（Q5 `researchkit-plan`）、収集（Q8 `researchkit-collect`）、分析（Q9 `researchkit-analysis`）が参照する。分析環境とコマンドの正本は `docs/method.md` と `.researchkit/config.yaml` の `commands` である。

出典の等級、確度、数値の規則は憲章（`.researchkit/memory/constitution.md`）に、再現性の水準は品質基準（`docs/quality.md`）に従う。

## いつ使うか

- 量で答える問い（規模、割合、変化、差、関係の強さ）で、使えるデータがあるとき
- 公開データ（統計の個票や表、オープンデータ）、社内データ、購入したデータ、アンケートの回答を集計・分析するとき
- デスクリサーチや文献レビューで得た数値を、再計算できる形にするとき（市場規模の推計、メタ分析）

向かない場面: データの定義や取り方が分からない（出所が説明できないデータは根拠にしない）、理由や動機を知りたい（定性調査）。

## 計画に書くこと（plan.md の節）

| plan.md の節 | 書くこと |
|---|---|
| 手法 | 分析の種類（記述、比較、関係、予測、推計） |
| データ | 使うデータ、出所、取得の方法、ライセンス・利用規約、`[人]` の要否 |
| 標本 | 対象の母集団、標本の取り方、期間、除外の条件、欠損の扱い |
| 分析の計画 | 指標の定義、比較の単位、統計の手法、有意水準か判断の基準、多重比較の扱い、見る効果量 |
| 仮説と反証条件 | 仮説を捨てる結果（例: 差の 95% 信頼区間が 0 を含む、効果量が 0.2 未満） |
| 検索数の見積もり | データの所在や定義を確かめる検索の回数 |

**分析の計画は、データを見る前に書く**（事前登録に当たる。steering の原則 4）。データを見た後で計画を変えたとき、または計画にない分析をしたときは、`plan.md` の「計画の変更」に書き、その分析を「探索的」と明示する。

## 収集の手順（データの取得と目録）

1. **取得する。** 公開データはダウンロードか API で取得する。取得はなるべくスクリプト（`studies/<NNN-name>/analysis/00_fetch.py` など）にし、URL と取得日を残す。社内データや購入したデータは `[人]` のタスクで入手してもらう。
2. **置き場所を決める。** `data.max_file_mb`（既定 5MB）未満は `data/raw/` に置いてコミットする。超えるものは `data/large/` に置き、コミットしない。
3. **`data/raw/` のファイルは加工しない。** 開いて保存し直すことも含めて、手を加えない。直しが要るときは、前処理のスクリプトで行い、結果を別の場所（`analysis/` の中間ファイルか `out/`）に出す。
4. **目録に書く。** `data/manifest.md` に 1 ファイル 1 行で、ファイルのパス、出所（出典 ID と URL）、取得日、ライセンス・利用規約、SHA-256 のハッシュ、大きさ、置き場所（`raw` か `large`）、内容の要約を書く。出典の台帳（`sources/<ID>.md`、`type: dataset`）にも登録する。
   - ハッシュの求め方の例: `shasum -a 256 <file>`（macOS）、`sha256sum <file>`（Linux）、`Get-FileHash <file> -Algorithm SHA256`（Windows の PowerShell）、または `python3 -c "import hashlib,sys;print(hashlib.sha256(open(sys.argv[1],'rb').read()).hexdigest())" <file>`
5. **定義を確かめる。** データの説明（コードブック、調査票、変数の定義、更新の履歴）を入手し、`evidence/` に要点を書く。説明が手に入らない変数は、分析の主な根拠にしない。
6. **個人情報を確かめる。** 個人を特定できる情報を含むデータは、扱ってよい範囲を確かめ（`[人]`）、分析の前に取り除くか仮名にする。リポジトリに入れてよいかも確かめる。

## 分析の手順

### 前処理

- 前処理はすべてスクリプトにする（手で表を直さない）。スクリプトは番号順に並べ（`01_clean.py`、`02_analyze.py`）、生データから最後の出力まで、順に実行すれば再現できるようにする。
- 実行は `.researchkit/config.yaml` の `commands.analysis`（`{script}` をスクリプトのパスに置き換える）で、プロジェクトのルートから行う。スクリプトの中のパスは、スクリプトの場所を基準に解決する。
- 取得（`curl -sS -o <ファイル>` など）も分析も、結果はファイルに書き、標準出力は件数・パス・主な値の数行にする（steering「コマンドの出力を短くする」）。
- 除外した行の数と理由、欠損の扱い、外れ値の扱いを、出力の JSON にも書く（母数が分かるように）。
- 乱数を使うときはシードを固定し、その値を出力に書く。

### EDA（探索的データ分析）

- 件数、欠損、分布、外れ値、時系列の切れ目（定義の変更、調査方法の変更）を確かめる。
- EDA で見つけたことで計画を変えるなら、「計画の変更」に書く。EDA の結果から仮説を作り、同じデータで確かめたように書かない（HARKing。Kerr, 1998）。

### 事前登録との対応

- `plan.md` の「分析の計画」の各項目に、実際に行った分析を対応させる。計画どおりの分析（確認的）と、計画にない分析（探索的）を分けて報告する。
- 反証条件に当たった結果は、隠さずに `findings.md` に書く。

### 出力（`analysis/out/*.json`）

報告に使う数値は、すべて `studies/<NNN-name>/analysis/out/<名前>.json` に出す。`numbers.py` が、本文の `{N:<path>#<key>}` と突き合わせる（steering の「数値の参照」）。

```json
{
  "n": 1250,
  "excluded": {"missing_outcome": 38, "duplicate": 4},
  "share_remote": 0.274,
  "diff_productivity": {"estimate": 0.12, "ci95": [0.03, 0.21], "cohens_d": 0.18},
  "seed": 20261003,
  "units": {"diff_productivity": "7 段階の尺度の点"}
}
```

- キーはドット区切りで参照できる入れ子にする（例: `diff_productivity.cohens_d`）。
- 割合は 0〜1 で持つ（`numbers.py` は JSON の値が 0〜1 なら 100 倍して `%` と比べる）。
- 単位はキー名か `units` に書く。
- 丸めはしない（丸めは報告の側で、憲章の規則に従う）。許容差は `config.yaml` の `numbers.tolerance`。
- `findings.md` では `27.4%{N:analysis/out/survey.json#share_remote}` のように書く。

### 図表

- 図は `analysis/out/fig/` に、スクリプトで作る。図の元の数値も CSV か JSON で残す。
- 軸の単位、母数、期間、出典を図か注記に書く。軸を 0 から始めない棒グラフなど、差を大きく見せる描き方をしない。

### 再実行の確認

- 分析を終えたら、生データから順にすべてのスクリプトを実行し直し、`out/` の値が変わらないことを確かめる。
- 目録のハッシュと、手元のファイルのハッシュが一致することを確かめる。
- テストがあれば `commands.test` を実行する。
- `$NUM --rq <NNN>` で、本文の数値と出力が一致することを確かめる。

## 統計的な注意

- **効果量と信頼区間を書く。** p 値だけで結論を出さない。p 値は効果の大きさや重要さを表さない（アメリカ統計学会の声明。Wasserstein と Lazar, 2016）。
- **多重比較。** 多くの検定をすると、偶然の「有意」が増える。検定の数を書き、必要なら補正（Bonferroni、Holm、Benjamini-Hochberg の偽発見率など）をする。補正をしないときは、探索的と明示する。
- **p ハッキング。** 有意になるまで、変数、除外の条件、手法を変えて試すことをしない（Simmons、Nelson、Simonsohn, 2011）。分析の選び方が結果を左右すること（分かれ道の多さ。Gelman と Loken）を意識し、試した分析をすべて記録する。
- **相関と因果。** 観察データの関係から因果を言わない。交絡（両方に効く第 3 の要因）、逆の因果、選択の偏りを検討する。因果を言うには、実験か、因果推論の手法と、その前提の説明が要る。
- **シンプソンのパラドックス。** 全体の傾向と、層ごとの傾向が逆になることがある。主要な層で分けて確かめる。
- **生態学的誤謬。** 集団の単位の関係を、個人の関係として読まない。
- **母数と分母。** 割合には母数（n）を添え、分母の定義（全体か、回答者か、該当者か）を書く。
- **標本の偏り。** 標本が母集団を代表するか（回答した人だけ、残った企業だけ）を書く。

## 記録するもの

| 記録 | 置き場所 |
|---|---|
| データの目録（出所、取得日、ライセンス、SHA-256） | `data/manifest.md` |
| データの出典 | `sources/<ID>.md`（`type: dataset`） |
| 変数の定義、コードブックの要点 | `studies/<NNN-name>/evidence/` |
| 取得・前処理・分析のスクリプト | `studies/<NNN-name>/analysis/` |
| 報告に使う数値 | `studies/<NNN-name>/analysis/out/*.json` |
| 図と、その元の数値 | `studies/<NNN-name>/analysis/out/fig/` |
| 計画の変更、探索的な分析 | `plan.md` の「計画の変更」 |

## よくある落とし穴

- **生データを手で直す。** 再現できなくなる。直しはスクリプトで行う。
- **出所の分からないデータを使う。** 誰が、いつ、どう集めたかを説明できないデータは根拠にしない。
- **定義の変更を見落とす。** 統計の調査方法や区分が途中で変わり、時系列に段差ができる。
- **有意になるまで試す。** 試した分析を記録せず、都合の良い結果だけを報告する。
- **割合の母数を書かない。**
- **相関から因果を言う。**
- **大きなファイルをコミットする。** `data.max_file_mb` を超えるものは `data/large/` に置く。
- **報告の数値を手で写す。** `{N:...}` を付けずに写すと、分析をやり直したときに食い違う。

## [人] になる作業

- 社内データの取得と、アクセス権の申請
- 購入するデータの契約と入手
- 個人情報を含むデータの扱いの判断（リポジトリに入れてよいか、匿名化の水準）
- データの定義について、提供元への問い合わせ

## 確かめること（手法を決めるとき）

- `uv` か R が使えるか（`uv --version`、`Rscript --version`）
- 使うデータのライセンスと利用規約（商用利用、再配布、加工したデータの公開）
- 公開データの API の利用条件と、取得の上限
