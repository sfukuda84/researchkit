# researchkit-review スキル（5 軸のレビュー）

調査の成果物を、**5 つの独立した軸**で審査し、直す。出典は実在するが主張が飛躍している、論理は通るが反対の証拠を探していない、数値は正しいが標本が偏っている、といった、1 つの軸だけでは見落とす問題を防ぐため、軸ごとに分けて見る。

外部の CLI には依存しない。エージェント自身のファイルの読み込み、機械検証（`$CHECK`・`$NUM`）、分析のスクリプトの再実行、Web 検索、サブエージェント（独立審査）で完結する。パスは既定の配置で書いている。`.researchkit/config.yaml` の `paths` で読み替える。`$RK`・`$CHECK`・`$NUM` の意味は steering（`.kiro/steering/research.md`）の「エージェントの行動規範」のとおりである。

## 1. 引数

```text
$ARGUMENTS
```

- 対象の指定は §3 の表に従う。
- `--axis <軸,...>` で軸を絞る（既定は 5 軸。対象の RQ の `**手法**` に `qualitative` か `data` があれば Ethics を足して 6 軸）。値は `source`、`logic`、`counter`、`bias`、`numbers`、`ethics`。
- `--round <n>` はレビューの回（RQ の工程の Q11 が 1、Q12 が 2）。記録のファイル名と、2 回目のレンズ（§4.2）に使う。単独で呼ばれたときは省略してよい（1 回目として扱う）。
- `--auto` は自動モード（§6）。

## 2. 軸

### 軸 S: Source（出典）

- **実在**: 根拠に使った出典が実在し、たどれるか。URL が開けるか、DOI が解決するか、題名・著者・年・誌名が一致するか。`$CHECK --rq <NNN> --online` の結果を材料にし、主張の確度が高いもの（`確実`・`可能性が高い`）と、決定（`D1` など）に効く主張の出典は、ページを開いて確かめる。
- **一次資料か**: 一次資料に当たれるのに、報道や要約で済ませていないか。二次資料が引く一次資料を確かめずに、一次資料として扱っていないか（孫引き）。
- **日付**: 発行日と参照日。問いの時点に対して古すぎないか（品質基準の鮮度の定め）。改訂版・新しい版が出ていないか。
- **等級**: 憲章の等級の定義どおりか。根拠が `sources.min_grade` を満たすか。等級 `D` を根拠にしていないか。
- **引用と原文の一致**: 抜き書き（`evidence/`）の引用が原文と一致するか、位置が正しいか、数値の単位・母数・期間が原文どおりか。主張が引用の範囲を越えて言っていないか。少なくとも、決定に効く主張の引用はすべて、ほかは抜き取りで照合する。
- **台帳の整合**: `used_in` と実際の参照、必須項目、`verified_by` の書き方。

### 軸 L: Logic（論理）

- **飛躍**: 主張が根拠から言えるか。根拠の言っていないこと（範囲、程度、時点）を足していないか。
- **相関と因果**: 因果を言える設計でないのに、因果の言葉（「〜により」「〜のため」）で書いていないか。交絡、逆の因果、選択の説明を検討したか。
- **一般化**: 標本・地域・期間・対象を越えて一般化していないか。少数の事例や発言から全体を言っていないか。
- **答えの形**: `spec.md` の「答えの形」に答えているか。「判定の基準」の判定が根拠と合っているか。範囲外のことを主張していないか。
- **確度と判定**: 確度が憲章の規則（`researchkit-findings` の確度の付け方）どおりか。仮説の判定（支持・棄却・保留）が反証条件どおりか。
- **主張どうしの整合**: 主張が互いに矛盾していないか。答え・決定への意味と主張が合っているか。

### 軸 C: Counter（反対の証拠と代わりの説明）

- **追加の検索**: 主な主張（決定に効くもの、確度の高いもの）ごとに、反対の証拠と代わりの説明を **Web で新しく検索する**。収集のときと違う検索語（否定の語、反対の立場の用語）、違う言語、違うデータベースを使う。検索した式と結果は、記録の「Counter の検索」の表に書く。
- **検索の十分さ**: `search-log.md` の反証の検索が、`plan.md` の反証条件ごとにあるか。件数と範囲は十分か。
- **反証条件の無視**: 反証条件に当たる結果を、例外や誤差として退けていないか。退けたなら、その理由が根拠を持つか。
- **代わりの説明**: 主張を説明する別の仮説（季節性、定義の変更、制度の変更、景気、測り方の違い）を検討したか。
- 見つかった反対の証拠は、出典の候補として URL と要点を記録に書く。採用するときは、親が `researchkit-collect` の手順（実在の確認、等級、抜き書き）で登録する。

### 軸 B: Bias（バイアス）

- **確証バイアス**: 仮説を支える資料だけを探していないか。検索語に結論が入っていないか（「〇〇 成功」だけで探す、など）。
- **選択バイアス・標本の偏り**: 標本の選び方（便宜的な標本、回答者の自己選択、特定の地域・時期）が結果を偏らせていないか。除外の基準が結果を有利にしていないか。
- **生存者バイアス**: 成功した事例・残った企業・続いている利用者だけを見ていないか。
- **出版バイアス**: 肯定的な結果の研究だけを拾っていないか。灰色文献を探したか（文献レビュー）。
- **スポンサーの利害**: 出典の作り手（企業、業界団体、調査の依頼主）に結果への利害がないか。この調査自体の依頼主の意向（`premises.md` の利害関係）が、結論の書き方に入っていないか。
- **事後の変更**: データを見た後に計画を変えた結果を、主として使っていないか（`plan.md` の「計画の変更」）。

### 軸 N: Numbers（数値）

- **突き合わせ**: `$NUM --rq <NNN>`（報告書は `$NUM --file <path>`）の結果。`{N:...}` の付いていない数値がないか。
- **計算**: `{N:calc}` の計算の表を検算する。割合の合計、増減率、年平均の成長率、単位の換算を確かめる。
- **単位・母数・期間**: 単位（千・百万・億）、割合とポイントの違い、母数（全体か回答者か）、期間（年度と暦年、時点と期間）、名目と実質（物価の扱い）、為替（どの時点のレートか）。
- **再実行**: `commands.analysis` で分析のスクリプトをすべて再実行し、`analysis/out/` の JSON が変わらないことを確かめる（`git diff --stat -- studies/<NNN-name>/analysis/out/` が空）。変わったら、乱数のシード、入力のハッシュ（`data/manifest.md`）、環境の違いを調べる。
- **原文との一致**: 出典から写した数値が、抜き書きの原文と一致するか（Source 軸と分担する。Numbers は値と単位、Source は引用の文）。

### 軸 E: Ethics（倫理・権利。定性調査とデータ分析で足す）

- **同意**: インタビュー・アンケートの同意の記録があるか（`[人]` のタスクの完了の確かめ方）。同意の範囲を越えて使っていないか。
- **匿名化**: `evidence/`、`analysis/`、`sources/`、`findings.md`、報告書に、名前・所属・連絡先など個人を特定できる情報がないか。属性の組み合わせや小さな区分で特定できないか。対応表がリポジトリに入っていないか。
- **ライセンスと利用規約**: `data/raw/` のデータを再配布してよいか（コミットしてよいか）。有料データベース・統計・レポートの利用規約の範囲か。図表の転載の許可。
- **引用の範囲**: 引用が必要な範囲にとどまり、出典が明示されているか。
- **AI 利用の開示**: 憲章の AI 利用の開示の定めを満たすか。
- 法的な判断はしない。判断に迷うものは `[人]` の確認に回す。

## 3. レビュー対象の特定

| 指定 | 対象 | 記録の置き場 |
|---|---|---|
| RQ（`001`、`001-market-size`）、または省略（今の worktree の RQ） | `studies/<NNN-name>/findings.md` を中心に、根拠の `evidence/`、`analysis/`、`search-log.md`、`plan.md`、使った `sources/` | `studies/<NNN-name>/reviews/review-<round>.md` |
| `999`、または RQ の工程の中の `reports/report.md` | `reports/report.md`、`reports/publish/`、`studies/999-research-report/findings.md`、報告書が参照する各 RQ の主張 | `studies/999-research-report/reviews/review-<round>.md` |
| ファイルのパス（工程の外。任意の報告書・資料） | そのファイルと、そこに書かれた出典 | `docs/reviews/<YYYYMMDD>-<対象>.md` |

- RQ の工程の外で RQ や報告書を見直すとき（`main` で後から見直すなど）も、記録は `docs/reviews/` に置く。
- 工程の外の資料で出典 ID がないものは、本文の出典の書き方（脚注、参考文献の一覧）を出典として扱い、Source 軸で 1 件ずつ確かめる。

## 4. 手順

### 4.1 始める前に

1. **予算**: Q11 として呼ばれたときは `$RK budget --step Q11` を実行する（呼び出し元が直前に確かめていれば省いてよい）。2 回目（Q12）と単独の実行では、Counter 軸の検索の見積もりで `$RK budget --need <件数>` を実行する。`VERDICT: STOP`（終了コード 4）なら始めずに止まる。自動モードでも止まる。新しいセッションで同じ引数で実行すれば、続きから再開する。
2. **文脈の読み込み**: 対象のファイルと、`spec.md`、`plan.md`、`docs/study/hypotheses.md`、憲章、`docs/quality.md`、`docs/questions/<NNN>.md`（`**手法**` と「つながる決定」）、`docs/concept/premises.md`（利害関係）を読む。
3. **機械検証**: `$CHECK --rq <NNN>`（Source 軸を含むときは `--online` も）と `$NUM --rq <NNN>` を実行し、結果を Source・Numbers の審査に渡す。報告書は `--file` で指定する。

### 4.2 独立審査（サブエージェント）

サブエージェント（Claude Code の Agent など）が使えるときは、軸ごとに 1 つずつ、**会話の文脈を持たない**サブエージェントに審査させる。主張を書いた本人の思い込みを持ち込まないためである。

- **渡すもの**: 軸の名前と §2 のその軸の観点、対象のファイルのパス、読むべき文書のパス、機械検証の結果（Source・Numbers）、出力の形式（§5 の指摘の形）。「落とす理由を探す」立場で審査させ、指摘ごとに根拠（ファイルと行、出典の URL とページの位置、検索の式と結果）を必ず付けさせる。
- **渡さないもの**: 収集と分析の経緯、親の判断、「たぶん問題ない」といった見立て。
- **書かせないもの**: 成果物とレビューの記録。サブエージェントは指摘を最終回答で返すだけにし、ファイルは親が書く。
- 軸どうしは並行に走らせてよい。Source と Counter は Web を使えるサブエージェントにする。Counter には、検索の件数の上限（予算の見積もりの範囲）を渡す。
- **2 回目（`--round 2`）のレンズ**: 1 回目の記録（`review-1.md`）と、1 回目の修正の差分（`git diff <Q11 のチェックポイント>..HEAD`、なければ `git diff HEAD~1`）を渡す。同じ指摘の繰り返しではなく、次を重点にさせる。
  - 1 回目の修正が正しく直っているか。修正で、ほかの主張・答え・仮説の判定・逆流した文書との食い違いが生まれていないか
  - 軸ごとに 1 回目と違うレンズ: Source は 1 回目に抜き取らなかった引用、Logic は答えと決定への意味、Counter は 1 回目と違う言語・データベース・立場からの検索、Bias は検索語とスポンサーの利害、Numbers はスクリプトの再実行と単位・期間、Ethics は報告書と公開用の形式への個人情報の持ち込み

サブエージェントが使えない環境では、親が軸を 1 つずつ、軸を切り替えるたびに観点を読み直して審査する。Counter 軸を先に行い、主張を読み返す前に反対の証拠を探す。

### 4.3 裏取りと採否

親は、サブエージェントの指摘をそのまま直さない。指摘ごとに次を行う。

1. 根拠のファイルと行、出典のページを自分で開いて確かめる。数値の指摘は、スクリプトの再実行か計算で再現する。
2. 採否を決める: **採用**（直す）、**不採用**（理由: 誤読、規則で許されている、根拠がない など）、**保留**（ユーザーの判断が要る）、**人の確認へ**（法的な判断、専門家の確認、同意の記録の確認など。`[人]` のタスクにする）。
3. 採否と理由を記録に残す（§5）。不採用の指摘も消さない。

### 4.4 修正

1. CRITICAL と HIGH の採用した指摘は、その場で直す。MEDIUM も原則直す。LOW は直すか、理由を書いて残す。
2. 直し方に応じて、元の工程の手順を使う。
   - 出典の差し替え・追加、抜き書きの訂正 → `researchkit-collect` の手順（実在の確認、等級、`$RK sources next`）
   - 分析の誤り、スクリプトの修正 → `researchkit-analysis` の手順（再実行、計画の変更の記録）
   - 主張・確度・判定の修正 → `researchkit-findings` の手順。主張を変えたら、逆流した文書（`hypotheses.md` など）も合わせる
   - 報告書の修正 → `researchkit-synthesize` の規則（新しい事実を足さない）
3. 直し方に複数の選択肢があるとき、主張の結論が変わるときは、推奨案（`**Recommended:**`）を添えて質問し、合意を得てから直す。工程の外の資料は、直す前に必ず確かめる。
4. 直した後、`$CHECK` と `$NUM` を再実行し、ERROR を 0 件にする。スクリプトを直したときは、再実行して出力が変わらない（または意図どおりに変わった）ことを確かめる。

## 5. 記録の様式

様式は [templates/review.md](./templates/review.md)。同じ回のファイルがあれば追記する（上書きしない）。

指摘の ID は `R<回>-<軸の頭文字><連番>`（例: `R1-N03`）。軸の頭文字は Source が `S`、Logic が `L`、Counter が `C`、Bias が `B`、Numbers が `N`、Ethics が `E` である。各指摘に、重大度、軸、場所（ファイルと行、主張の ID）、根拠、直し方、採否を書く。

| 重大度 | 目安 |
|---|---|
| CRITICAL | 出典が実在しない、等級 `D` を根拠にした、引用が原文と違う・原文にない、数値が出力や原文と一致しない、反証条件に当たる結果を無視した判定、個人を特定できる情報、同意や利用規約に反するデータ、憲章の違反 |
| HIGH | 主張と根拠の飛躍、相関を因果として書いた、範囲を越えた一般化、確度の過大、主要な反対の証拠の見落とし、孫引き、単位・母数・期間の誤り、答えの形に答えていない、スクリプトを再実行すると結果が変わる |
| MEDIUM | 古い出典、一次資料に当たれるのに二次資料、検索語の偏り、限界の書き漏れ、主張を変えない等級の付け誤り、計画の変更の記録漏れ |
| LOW | 表記、軽微な改善 |

## 6. 自動モード（`--auto`）

RQ の工程から呼ばれたときは、`researchkit-worktree` の自動モードの規則に従い、自動で決めたことを `studies/<NNN-name>/auto-decisions.md` に記録する。

| 場面 | 自動モードでの動作 |
|---|---|
| 採用した CRITICAL・HIGH・MEDIUM の修正 | 推奨案で直す。主張の結論や確度が変わる修正は、`auto-decisions.md` に見直しの優先度「高」で記録する |
| 不採用の判断 | 記録に理由を書いて進む |
| 保留にしたい指摘 | 推奨案を採る。決められないもの（決定・前提が崩れる、憲章・品質基準・`docs/method.md` の変更が要る）は止まる |
| 人の確認へ | `tasks.md` に `[人]` のタスクを足し、自動で完了にしない |
| Counter 軸で見つかった反対の証拠 | 登録して主張に反映する（確度を下げる、反証・限界に書く）。結論が覆るときは止まる |

止まる場面: 予算の STOP、上の表の止まる場合、同じ原因の失敗が 3 回続いた場合。

## 7. 出力

- `studies/<NNN-name>/reviews/review-<round>.md`（工程の外は `docs/reviews/<YYYYMMDD>-<対象>.md`。様式: [templates/review.md](./templates/review.md)）
- 修正した成果物（`findings.md`、`evidence/`、`analysis/`、`sources/`、逆流した文書、報告書）
- `tasks.md` に足した `[人]` のタスク（人の確認へ回したもの）

RQ の工程では、1 回目（Q11）の次は 2 回目のレビュー（Q12）、2 回目の次は `researchkit-worktree` の Q13（マージ）である。チェックポイント（`review(<RQ>): 5 軸レビュー（1 回目）`・`（2 回目）`）は呼び出し元（`researchkit-execute`・`researchkit-all`）が記録する。工程の外で単独で呼ばれたときは、チェックポイントを記録せず、記録と修正を通常のコミット（`review: <対象> のレビュー`）にしてよいかを確かめる。

## 8. 完了報告

- 記録のファイルのパス
- 軸ごとの指摘の件数（重大度別）と採否
