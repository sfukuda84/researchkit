# researchkit-review スキル（5 軸のレビュー）

調査の成果物を、**5 つの独立した軸**で審査し、直す。出典は実在するが主張が飛躍している、論理は通るが反対の証拠を探していない、数値は正しいが標本が偏っている、といった、1 つの軸だけでは見落とす問題を防ぐため、軸ごとに分けて見る。

外部の CLI には依存しない。エージェント自身のファイルの読み込み、機械検証（`$CHECK`・`$NUM`）、分析のスクリプトの再実行、Web 検索、サブエージェント（独立審査）で完結する。パスは既定の配置で書いている。`.researchkit/config.yaml` の `paths` で読み替える。`$RK`・`$CHECK`・`$NUM` の意味は steering（`.kiro/steering/research.md`）の「エージェントの行動規範」のとおりである。

## 1. 引数

```text
$ARGUMENTS
```

- 対象の指定は §3 の表に従う。
- `--axis <軸,...>` で軸を絞る（既定は 5 軸。対象の RQ の `**手法**` に `qualitative` か `data` があれば Ethics を足して 6 軸）。値は `source`、`logic`、`counter`、`bias`、`numbers`、`ethics`。
- `--round <n>` はレビューの回（RQ の工程の Q11 が 1、Q12 が 2）。記録のファイル名と、2 回目のレンズ（§4.2）に使う。単独で呼ばれたときは省略してよい（1 回目として扱う）。
- `--auto` は自動モード（§6）。

## 2. 軸

### 軸 S: Source（出典）

出典が実在してたどれるか、一次資料か（孫引き）、日付と新しい版、等級、引用と原文の一致（決定に効く主張の引用はすべて、ほかは抜き取り）、台帳の整合。観点の全文は [references/axes.md](references/axes.md)。

### 軸 L: Logic（論理）

主張と根拠の飛躍、相関と因果、一般化、答えの形と判定の基準、確度と仮説の判定が規則どおりか、主張どうしの整合。観点の全文は [references/axes.md](references/axes.md)。

### 軸 C: Counter（反対の証拠と代わりの説明）

主な主張ごとに反対の証拠と代わりの説明を Web で新しく検索する（収集と違う語・言語・データベース）。反証の検索の十分さ、反証条件に当たる結果の無視、代わりの説明。見つかった証拠は URL と要点を書き、採用は親が `researchkit-collect` の手順で登録する。Counter の検索は親が `search-log.md` にも足す。観点の全文は [references/axes.md](references/axes.md)。

### 軸 B: Bias（バイアス）

確証バイアス（検索語）、選択バイアスと標本の偏り、生存者バイアス、出版バイアス、スポンサーの利害、事後の変更。観点の全文は [references/axes.md](references/axes.md)。

### 軸 N: Numbers（数値）

`$NUM` の突き合わせ、`{N:calc}` の検算、単位・母数・期間・名目と実質、スクリプトの再実行で出力が変わらないこと、原文との一致。観点の全文は [references/axes.md](references/axes.md)。

### 軸 E: Ethics（倫理・権利。定性調査とデータ分析で足す）

同意、匿名化、ライセンスと利用規約（再配布、図表の転載）、引用の範囲、AI 利用の開示。法的な判断はせず `[人]` に回す。観点の全文は [references/axes.md](references/axes.md)。

## 3. レビュー対象の特定

RQ（`findings.md` と根拠）なら記録は `studies/<NNN-name>/reviews/review-<round>.md`、`999` や `reports/report.md` なら `studies/999-research-report/reviews/`、工程の外のファイルなら `docs/reviews/<YYYYMMDD>-<対象>.md`。表と、出典 ID のない資料の扱いは [references/record.md](references/record.md)。

## 4. 手順

### 4.1 始める前に

1. **予算**: Q11 として呼ばれたときは `$RK budget --step Q11 --rq <RQ_NAME>` を実行する（呼び出し元が直前に確かめていれば省いてよい）。2 回目（Q12）と単独の実行では、Counter 軸の検索の見積もりで `$RK budget --need <件数>` を実行する。`VERDICT: STOP`（終了コード 4）なら始めずに止まる。自動モードでも止まる。新しいセッションで同じ引数で実行すれば、続きから再開する。
2. **文脈の読み込み**: 対象のファイルと、`spec.md`、`plan.md`、`docs/study/hypotheses.md`、憲章、`docs/quality.md`、`docs/questions/<NNN>.md`（`**手法**` と「つながる決定」）、`docs/concept/premises.md`（利害関係）を読む。
3. **機械検証**: `$CHECK --rq <NNN>`（Source 軸を含むときは `--online` も）と `$NUM --rq <NNN>` を実行し、結果を Source・Numbers の審査に渡す。報告書は `--file` で指定する。

### 4.2 独立審査（サブエージェント）

サブエージェント（Claude Code の Agent など）が使えるときは、軸ごとに 1 つずつ、**会話の文脈を持たない**サブエージェントに審査させる。主張を書いた本人の思い込みを持ち込まないためである。

- **前提の定型**: サブエージェントへの指示は、[templates/brief.md](./templates/brief.md)（審査の前提の定型）を埋めて作る。自由に書き起こさない。共通の節（対象、審査する状態、値と分析の出どころ、まだないもの、守ること、最終回答の形）は全軸で同じ文面にし、軸の節（観点、2 回目の重点、Web の上限）だけを変える。埋めた前提の要点（審査した状態、渡した不採用の一覧）は `review-<n>.md` の「審査の方法」に書く。
- **渡すもの**: 軸の名前と §2 のその軸の観点、対象のファイルのパス、読むべき文書のパス、審査する状態（コミット、または未コミットの変更を含む作業ツリー）、値と分析の出どころ（`analysis.md` の前処理の記録と「探索的な分析」の表）、機械検証の結果（Source・Numbers）、出力の形式（§5 の指摘の形）。「落とす理由を探す」立場で審査させ、指摘ごとに根拠（ファイルと行、出典の URL とページの位置、検索の式と結果）を必ず付けさせる。
- **渡さないもの**: 収集と分析の経緯、親の判断、「たぶん問題ない」といった見立て。
- **書かせないもの**: 成果物とレビューの記録。サブエージェントは指摘を最終回答で返すだけにし、ファイルは親が書く。
- 軸どうしは並行に走らせてよい。ただし同時に動かすのは `subagents.max_parallel`（既定 3）までにし、5〜6 軸は組に分ける（例: Source・Counter・Numbers の組の後に Logic・Bias・Ethics の組）。モデルは `subagents.model`（既定 `sonnet`）を指定する。指摘の裏取りと修正は親が行う（§4.3）。
- Source と Counter は Web を使えるサブエージェントにする。Counter には、検索の件数の上限（予算の見積もりの範囲）を渡す。
- 最終回答は指摘の表（場所・重大度・根拠・直し方）だけにさせ、読んだファイルの中身や検索の経過を返させない。
- **2 回目（`--round 2`）のレンズ**: 1 回目の記録（`review-1.md`）と、1 回目の修正の差分（`git diff <Q11 のチェックポイント>..HEAD`、なければ `git diff HEAD~1`）を渡す。その回の記録（`review-2.md`）と、その回の検索の `search-log.md` への追記は、審査の後に親が書くので、まだないことも伝える（ないことを指摘させない）。1 回目に不採用・人の確認へにした指摘の一覧と理由を渡し、同じ指摘をするなら 1 回目の理由を覆す新しい根拠を付けさせる（定型の「2 回目のとき」の節）。同じ指摘の繰り返しではなく、次を重点にさせる。
  - 1 回目の修正が正しく直っているか。修正で、ほかの主張・答え・仮説の判定・逆流した文書との食い違いが生まれていないか
  - 軸ごとに 1 回目と違うレンズ: Source は 1 回目に抜き取らなかった引用、Logic は答えと決定への意味、Counter は 1 回目と違う言語・データベース・立場からの検索、Bias は検索語とスポンサーの利害、1 回目の修正で足した探索的な分析が片方の側にだけ使われていないか（§4.4 の「両方向」）と、事前の規則を結果を見た後に読み直していないか、Numbers はスクリプトの再実行と単位・期間、Ethics は報告書と公開用の形式への個人情報の持ち込み

サブエージェントが使えない環境では、親が軸を 1 つずつ、軸を切り替えるたびに観点を読み直して審査する。Counter 軸を先に行い、主張を読み返す前に反対の証拠を探す。

### 4.3 裏取りと採否

親は、サブエージェントの指摘をそのまま直さない。指摘ごとに次を行う。

1. 根拠のファイルと行、出典のページを自分で開いて確かめる。数値の指摘は、スクリプトの再実行か計算で再現する。
2. 採否を決める: **採用**（直す）、**不採用**（理由: 誤読、規則で許されている、根拠がない など）、**保留**（ユーザーの判断が要る）、**人の確認へ**（法的な判断、専門家の確認、同意の記録の確認など。`[人]` のタスクにする）。
3. 採否と理由を記録に残す（§5）。不採用の指摘も消さない。

### 4.4 修正

1. CRITICAL と HIGH の採用した指摘は、その場で直す。MEDIUM も原則直す。LOW は直すか、理由を書いて残す。
2. 直し方に応じて、元の工程の手順を使う。
   - 出典の差し替え・追加、抜き書きの訂正 → `researchkit-collect` の手順（実在の確認、等級、`$RK sources next`）
   - 分析の誤り、スクリプトの修正 → `researchkit-analysis` の手順（再実行、計画の変更の記録）
   - 主張・確度・判定の修正 → `researchkit-findings` の手順。主張を変えたら、逆流した文書（`hypotheses.md` など）も合わせる
   - 報告書の修正 → `researchkit-synthesize` の規則（新しい事実を足さない）
3. **分析の「修正」と「追加」を分ける。** 指摘に答えるために分析を変えるときは、次のどちらかを先に決め、`plan.md` の「計画の変更」に書く。

   | 種類 | 例 | 扱い |
   |---|---|---|
   | 修正 | 事前に決めた分析の誤りを直す（行の読み違い、計算の誤り、単位の取り違え） | 主の値を直してよい。「計画の変更」に「誤りの修正（R1-N01）」と書く。確度の付け方と判定の規則は変えない |
   | 追加 | 指摘に答えるため、事前に決めていない分析（感度、別の指標、除外の組み合わせ）を足す | 探索的な分析として扱う（下の規則）。「計画の変更」の「結果を見た後か」は「後（レビュー R1-C01）」 |

   追加した分析の規則（憲章の確認的と探索的の区別）:
   - **出力の置き場**: JSON の `exploratory` の下に置く（例: `calorie.json#exploratory.coef_chain`）。`analysis.md` の「探索的な分析」の表に 1 行足す（`researchkit-analysis` の §4.3）。
   - **主張**: 結果は別の主張にし、確度は「示唆」までにする。既存の主張の文や確度の理由に混ぜない（反証・限界の欄で触れるのはよい）。主張の欄で `{N:…#exploratory.…}` を使う主張の確度が高いと、`$CHECK` が `EXPLORATORY_CONFIDENCE` で止める。
   - **判定に使わない**: 主の値、事前に決めた主張の確度、仮説の判定の根拠にしない。確度を上げる方向にも、下げる方向にも使わない。
   - **両方向**: ある側の結果を弱める（説明する）ための分析を足すときは、反対の側に動きうる分析も同じ回で検討し、足すか、足さない理由を記録に書く。片方の側にだけ使わない。
   - **事前の規則を読み直さない**: 確度の付け方の表などは、結果を見た後に都合のよい読み方を決めない。曖昧なら字面どおりか、確度が低くなる側を採り、その読み方を記録する。
4. 直し方に複数の選択肢があるとき、主張の結論が変わるときは、推奨案（`**Recommended:**`）を添えて質問し、合意を得てから直す。工程の外の資料は、直す前に必ず確かめる。
5. 直した後、`$CHECK` と `$NUM` を再実行し、ERROR を 0 件にする。スクリプトを直したときは、再実行して出力が変わらない（または意図どおりに変わった）ことを確かめる。

## 5. 記録の様式

様式は [templates/review.md](./templates/review.md)。同じ回のファイルには追記する。指摘の ID は `R<回>-<軸の頭文字><連番>`（S・L・C・B・N・E）。各指摘に重大度・軸・場所・根拠・直し方・採否を書く。重大度は CRITICAL（実在しない出典、等級 D を根拠、原文・出力と違う引用や数値、反証条件の無視、個人情報、憲章の違反）、HIGH（飛躍、相関を因果、一般化、確度の過大、反対の証拠の見落とし、孫引き、単位・期間の誤り、再実行で結果が変わる）、MEDIUM（古い出典、検索語の偏り、限界の書き漏れ、計画の変更の記録漏れ）、LOW（表記）。重大度の表の全文は [references/record.md](references/record.md)。

## 6. 自動モード（`--auto`）

採用した CRITICAL・HIGH・MEDIUM は推奨案で直す（結論や確度が変わる修正、指摘に答えて足した分析は `auto-decisions.md` に優先度「高」）。不採用は理由を書く。人の確認へ回すものは `[人]` のタスクにし、自動で完了にしない。Counter 軸の反対の証拠は登録して主張に反映し、結論が覆るときは止まる。予算の STOP、決定・前提・憲章の変更が要るとき、同じ原因の失敗が 3 回のときも止まる。表は [references/record.md](references/record.md)。

## 7. 出力

出力は記録（`review-<round>.md`）、修正した成果物、足した `[人]` のタスク。1 回目の次は 2 回目、2 回目の次は Q13。チェックポイントは呼び出し元が記録する。詳細は [references/record.md](references/record.md)。

## 8. 完了報告

完了報告の項目（記録のパス、軸ごとの件数と採否、直した指摘と変わった主張、Counter の検索、保留と判断してほしい事項、人の確認へ、`$CHECK`・`$NUM`・再実行の結果、次の案内）は [references/record.md](references/record.md)。
