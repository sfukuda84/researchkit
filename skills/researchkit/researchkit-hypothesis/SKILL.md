# researchkit-hypothesis スキル（R5: イシューツリーと仮説）

調査は、調べるほど材料が増えて結論がぼやける。そこで、集め始める前に **何に答えれば決定できるか（イシューツリー）** と、**今の時点での答えの見込みと、それを捨てる条件（仮説と反証条件）** を決める（steering の基本原則 4）。以降の工程（予備調査、RQ の切り出し、計画、主張のまとめ）は、すべてこの 2 つを基準にする。

パスは `.researchkit/config.yaml` の `paths` で読み替える（既定は `docs/concept/`、`docs/study/`）。進捗の記録とモードは [`researchkit-bootstrap`](../researchkit-bootstrap/SKILL.md) の §3・§7 に従う。

## 0. 考え方の出どころ

| 考え方 | 出どころ | このスキルでの使い方 |
|---|---|---|
| MECE（漏れなく、重なりなく） | Barbara Minto『The Pyramid Principle』（マッキンゼーで広まった考え方） | 同じ親の下の子の問いが、重ならず、合わせると親の問いに答え切れるように分ける |
| ピラミッド原則 | 同上 | 上の問いに下の問いが答える縦の関係と、同じ階層の問いをまとめる横の関係で木を組む。根の問いは、状況（Situation）・複雑化（Complication）・問い（Question）の流れ（SCQ）で導く |
| イシュー度と解の質 | 安宅和人『イシューからはじめよ』（英治出版、2010） | 葉の問いの優先度を、その問いに答える必要の高さ（イシュー度）で決める。「解の質」を上げる前に、イシュー度の高い問いを選ぶ |
| 良いイシューの 3 条件 | 同上 | 本質的な選択肢である（答えで決定が変わる）、深い仮説がある（常識と違う見込みを含みうる）、答えを出せる（手に入る証拠で答えが出る）で葉を点検する |
| 仮説ドリブン | 同上（仮説から始め、仮説を検証する形で分析を設計する） | 葉ごとに、今の見込み（仮説）を先に書き、確かめる証拠と捨てる条件を決める |

## 1. 入力

- `docs/concept/premises.md`（RP1〜RP12。とくに RP2 決めたいこと、RP3 範囲、RP7 要求する確度）
- `docs/concept/framing.md`（選んだ型、中心の問い、下位の問い、答えの形、範囲外）
- `docs/concept/seed.md`（決定 D1〜、決め方の規則）
- `docs/scan/wide.md`（すでに分かっていること、まだ分かっていないこと、データの所在、論点と立場、代わりの説明）
- 引数の `--adopt <パス>`: 既存の論点整理、仮説の一覧、ロジックツリー

`premises.md` に、RP1〜RP4 が「未決」のまま残っていれば、`researchkit-sparring` を案内して止まる。ユーザーが後で決めると明示した項目は、`[NEEDS CLARIFICATION: ...]` のまま進めてよい。

## 2. 手順

### ステップ 1: 根の問いを決める

1. `framing.md` の中心の問いを、根の問い（I0）にする。SCQ で 3 行に書く（状況: 読み手が知っていること / 複雑化: なぜ今それが問題か / 問い: 何に答えるか）。
2. 根の問いの答えの形（`framing.md`）と、つながる決定（D）を書く。

### ステップ 2: イシューツリーを作る

1. 根の問いを、答えると根の問いに答えられる第 1 層の問い（I1、I2、…）に分ける。`framing.md` の下位の問いを出発点にする。分け方は、次のどれかで MECE を作る。
   - **式で分ける**: 答えが数値なら、計算の式に分ける（例: 市場の大きさ = 対象の企業数 × 利用率 × 1 社あたりの年間支出）
   - **分類で分ける**: 地域、顧客の層、製品の種類など、重ならない分類の軸で分ける
   - **過程で分ける**: 認知 → 検討 → 購入 → 継続のような段階で分ける
   - **賛否で分ける**: 「〇〇すべきか」は、効果があるか、実行できるか、危険は許せるか、のように判断の条件で分ける
2. 第 1 層を、答えが出せる大きさになるまで第 2 層（I1.1、I1.2、…）、必要なら第 3 層（I1.2.1）に分ける。深さは 3 層までを目安にする。それより深くなるなら、根の問いが大きすぎる（R3 の範囲の見直しを提案する）。
3. **葉**（それ以上分けない問い）ごとに、次を書く。
   - 問い（疑問文）と答えの形
   - つながる決定（D）。どの D にもつながらない葉は、ツリーから外して `backlog.md` に送る
   - すでに分かっているか（`wide.md` の「すでに分かっていること」で答えがある葉は「既知」とし、出典を書く。調べ直さない）
   - 良いイシューの 3 条件の点検（本質的な選択肢 / 深い仮説 / 答えを出せる。◎○△）
   - 優先度（高 / 中 / 低）。イシュー度（答えで決定が変わる度合い × 今の見込みの不確かさ）で決める
4. **MECE を点検する**。同じ親の下の子について、重なっている問いがないか、子にすべて答えても親に答えられない抜けがないかを確かめる。抜けを埋めないと決めた場合は、その理由と範囲外であることを書く。
5. ツリーの図を Mermaid で書く。

> 💬 ツリーの第 1 層と、優先度の高い葉を示し、合意を取る（AskUserQuestion。最大 2 問）。

### ステップ 3: 仮説を立てる

優先度が高・中の葉ごとに、今の時点での答えの見込みを、**反証できる形**で書く（H1〜。全体で 3〜10 個）。1 つの葉に複数の仮説があってよい。

各仮説に、次を書く。

| 項目 | 内容 |
|---|---|
| 仮説 | 観察やデータで真偽を判定できる文。範囲（地域、期間、対象）と数値の境目を入れる |
| 対応する葉 | I の ID |
| 決定への効き | 支持されたら D のどの選択肢を選び、棄却されたらどれを選ぶか。どちらでも同じなら、その仮説は要らない |
| 反証条件 | こうなったら仮説は誤り、と言える観察。測れる形で書く（例: 「公的統計 S000-0201 で、2020〜2024 年の年平均の伸びが 3% 未満」）。RP7（要求する確度）に合わせて厳しさを決める |
| 検証に要る証拠 | 種類（統計、文献、自社データ、インタビュー）、所在（`wide.md` の C の番号か出典 ID）、手に入るか（公開 / 申請 / 有料 / 不明） |
| 事前の見込み | 高 / 中 / 低と、その根拠（`wide.md` の出典。根拠がなければ「推測」） |
| 対立仮説・代わりの説明 | 同じ観察を別の理由で説明する仮説（`wide.md` の E を材料にする）。反対の証拠を探すときの手がかりにする（steering の基本原則 7） |
| 確かめ方の見込み | デスクリサーチ / 文献レビュー / データ分析 / 定性調査（R7 で決める） |
| 状態 | 未検証（この段階はすべて未検証） |

- 良い例: 「H2: 国内の従業員 20 人以下の企業で、クラウド会計の利用率は 2020〜2024 年に年 5% 以上伸びている。反証: 利用率の統計か複数の独立した調査で、年平均の伸びが 3% 未満」
- 悪い例: 「クラウド会計は伸びている」（範囲も、何が起きたら誤りかもない）
- 探索型の調査で、葉に見込みが立たない場合は、「仮説なし（探索）」とし、何が見つかれば問いに答えたことにするか（例: 「要因の候補が 3 つ以上、それぞれ 2 件以上の独立した出典で挙がる」）を反証条件の代わりに書く。
- 最も危うい仮説（外れたら決定が逆になり、事前の見込みが不確かなもの）を先頭に置く。

### ステップ 4: 分析の出力を先に描く（絵コンテ）

優先度が高い仮説ごとに、答えが出たときに見せる表か図の形を、空の枠で描く（『イシューからはじめよ』の「絵コンテ」。例: 「年 × 利用率の折れ線。2020〜2024。境目の 5% の線を引く」）。必要な証拠の抜けと、判定の基準のあいまいさが見つかる。`hypotheses.md` の各仮説の「出力のイメージ」に書く。

### ステップ 5: 点検

- すべての決定（D）に、少なくとも 1 本の葉と 1 つの仮説（または「仮説なし（探索）」の葉）がつながっているか。
- すべての仮説に、反証条件と、決定への効きがあるか。決定への効きが「どちらでも同じ」の仮説は外す。
- 反証条件が、手に入りそうな証拠で判定できるか（`wide.md` の C）。判定できない仮説は、R6 の予備調査の最初の対象にする。
- 対立仮説がない仮説が、全体の半分を超えていないか（確証バイアスの兆し）。
- 範囲（RP3）の外の問いが、ツリーに入っていないか。

## 3. 出力と記録

| ファイル | 内容 |
|---|---|
| `docs/study/issue-tree.md` | イシューツリー（[templates/issue-tree.md](templates/issue-tree.md)） |
| `docs/study/hypotheses.md` | 仮説と反証条件（[templates/hypotheses.md](templates/hypotheses.md)） |
| `docs/concept/backlog.md` | ツリーから外した問い（追記） |

`researchkit-bootstrap` から呼ばれたときは、bootstrap がコミットする。単独で実行したときも同じ形で記録する（bootstrap の再開の判定に使うため）。

```bash
git add -A
git commit --allow-empty -m "docs(bootstrap): R5 イシューツリーと仮説を作成" -m "Researchkit-Bootstrap: R5"
```

更新モード・取り込みのときは、subject を `docs(study): イシューツリーと仮説を更新` にし、trailer を付けない（R5 の完了はすでに記録されている。まだ記録がない取り込みでは、上の形で記録する）。

## 4. 更新モード（`--update`）と取り込み（`--adopt`）

- **更新**: `issue-tree.md` か `hypotheses.md` がすでにあるときは更新モードで動く。見直しの理由（予備調査の判定、RQ の主張のまとめ〈逆流。steering の基本原則 10〉、範囲の変更）を受け取り、変更の差分を示して合意を取ってから直す。
  - **ID を振り直さない。** 消した節や仮説は「取り下げ（理由）」と書いて残す。`docs/questions/` と `studies/` が ID を参照しているためである。新しい節や仮説は、既存の最大の番号の次から振る。
  - 仮説の状態は、`未検証`／`支持`／`棄却`／`保留` のどれかにし、変えたときは根拠（`studies/<NNN-name>/findings.md` の主張の ID か、`docs/study/pilot/results.md` の節）を書く。
  - 直したら、影響を洗い出す。仮説を変えたとき: その仮説を「つながる仮説」に持つ RQ（`docs/questions/`）と、その RQ の `plan.md` の反証条件。ツリーを変えたとき: RQ の切り方と `spec_order.md`。影響の一覧を完了報告に書き、RQ の更新は `researchkit-questions` を案内する（このスキルでは書き換えない）。
  - 両ファイルの「変更の記録」に 1 行足す。
- **取り込み**: 既存の論点整理や仮説の一覧を読み、ツリーと仮説に当たる記述を移し替える。元のファイルは動かさず、消さない。移し替えた記述には「出典: <元のファイル>§<節>」を添える。既存の記述に反証条件や決定への効きがなければ、ステップ 3 で足す。

## 5. 自動モード（`--auto`）

`researchkit-bootstrap` の `--auto`・`--oneshot` から呼ばれたときは、bootstrap §7 の規則に従う。単独の `--auto` も同じ扱いにする。

| 論点 | 自動モードでの動作 |
|---|---|
| ツリーの分け方 | 答えが数値なら式で、選択なら判断の条件で分ける。それ以外は `framing.md` の下位の問いをそのまま第 1 層にする |
| 葉の優先度 | 決定への効きが大きく、`wide.md` で答えが出ていないものを高にする |
| 仮説の選び方 | 外れたら決定が逆になるものから 3〜6 個 |
| 反証条件の厳しさ | RP7 の確度に合わせる。RP7 が仮定なら、独立した 2 件以上の出典で反対の結果が出たら棄却、を既定にする |
| 更新モードでの仮説の取り下げ | 取り下げは自動では行わない。取り下げの案を書いて止まる（RQ の工程から逆流で呼ばれたときは、状態を `棄却` にするまでを行い、取り下げはユーザーに委ねる） |

自動で決めたことは `docs/auto-decisions.md` の「R5」の節に書く。ツリーの第 1 層の切り方と、最も危うい仮説の選択は、見直しの優先度を「高」にする。

## 6. 完了報告

- 根の問いと、第 1 層の問い、葉の数（優先度別、既知の葉の数）
- 仮説の一覧（危うい順）と、反証条件・決定への効きの要約
- 反証条件を判定できるか不確かな仮説（R6 で最初に確かめるもの）
- 点検で見つかった食い違いと、どう直したか
- 次の案内: `researchkit-pilot` で問いが答えられるかを確かめる（bootstrap の中なら R6 に進む）

## 7. 規則

- 葉と仮説は少なく、強くする。決定に効かない問いは、面白くても `backlog.md` に送る。
- 反証条件のない仮説、決定への効きのない仮説で、完了にしない。
- 仮説の中の事実（「〇〇は 100 億円である」）を、出典なしに確かなこととして書かない。見込みとして書き、根拠の欄に出典か「推測」と書く。
- 応答と成果物は、プロジェクトの言語ルール（`.kiro/steering/language.md`）に従う。
