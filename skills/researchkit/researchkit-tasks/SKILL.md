# researchkit-tasks スキル（Q6: タスク）

調査計画を、そのまま実行できる作業の列にする。各タスクは、ほかの文脈がなくても AI が実行できるほど具体的に書き、終わったかどうかを確かめられる形にする。実行の工程（Q8〜Q10）は、このファイルの未完了のタスクを上から片付け、`- [x]` にしていく。

ステップ番号、モード、質問の規則は [`researchkit-worktree`](../researchkit-worktree/SKILL.md) に従う。通常は [`researchkit-question`](../researchkit-question/SKILL.md) か [`researchkit-all`](../researchkit-all/SKILL.md) から呼ばれる。チェックポイント（Q6）は呼び出した統括スキルが記録する。単独で実行したときは、最後に `$HELPER checkpoint <RQ_NAME> Q6 "<『ステップ番号』の節の subject>"` を記録する。パスは `.researchkit/config.yaml` の `paths` で読み替える。

## 1. 対象と入力

- 対象: `studies/<RQ_NAME>/tasks.md`（以下 `RQ_DIR/tasks.md`）。テンプレートは [`templates/tasks.md`](templates/tasks.md)。
- 必須: `RQ_DIR/spec.md`（小問 `SQ`、判定の基準 `AC`）、`RQ_DIR/plan.md`（手法、情報源と検索式、標本、データ、分析の計画、反証条件、反対の証拠の探し方、倫理）。どちらかがなければ、欠けている工程（`researchkit-specify`、`researchkit-plan`）を案内して止まる。
- 参照: 手法の参照文書 `researchkit-method/references/`（`plan.md` で選んだもの。手法ごとの作業の順序と `[人]` の典型）、憲章、`docs/quality.md`、`data/manifest.md`、`.researchkit/config.yaml` の `commands`

## 2. 書式

```text
- [ ] T001 [P] [SQ1] [人] 本文（対象のファイル）（完了の確かめ方: …）
```

| 部分 | 規則 |
|---|---|
| チェックボックス | 必ず `- [ ]` で始める |
| タスク ID | `T001` から実行の順に通しで振る |
| `[P]` | 並行してよいタスクにだけ付ける（別のファイルを扱い、未完了のタスクに依存しない） |
| `[SQn]` | 収集と分析のフェーズのタスクに付け、どの小問のためかを示す。複数なら `[SQ1,SQ2]`。準備とまとめのフェーズでは付けない |
| `[人]` | 人が行うタスクにだけ付ける（§3）。印は `[P]`・`[SQn]` の後、本文の前に置く |
| 本文 | 何をするかを動詞で書き、対象のファイルかディレクトリのパスを含める |
| 完了の確かめ方 | すべてのタスクの末尾に `（完了の確かめ方: …）` を書く。`[人]` のタスクでは必須である（steering の「人が行うタスク」）。ファイルの有無、件数、コマンドの結果など、AI が確かめられる形にする |

例:

- `- [ ] T001 出典 ID の範囲を取る（researchkit.py sources next 003 --count 30）（完了の確かめ方: plan.md の「出典 ID」に範囲が書かれている）`
- `- [ ] T004 [P] [SQ1] 情報源 1（e-Stat）の該当の表を取得し、data/raw/ に置いて data/manifest.md に記載する（完了の確かめ方: manifest に出所・取得日・ライセンス・ハッシュがある）`
- `- [ ] T005 [P] [SQ1] [人] 調査会社の有料レポート〈名前〉を購入するかを判断し、購入したら PDF を data/large/ に置く（完了の確かめ方: data/manifest.md に記載があり、ハッシュが一致する。購入しない場合は plan.md の「計画の変更」に記録がある）`
- `- [ ] T006 [SQ1] T005 で入手したレポートの該当の数値を抜き書きし、evidence/ と sources/ に記録する（完了の確かめ方: 出典ファイルの grade と accessed があり、check.py の ERROR が 0 件）`
- 誤り: `- [ ] 文献を集める`（ID、対象のファイル、完了の確かめ方がない）

## 3. `[人]` の付け方

steering の「人が行うタスク」に従う。要点は次のとおりである。

- タスクは AI が実行するものを基本とし、AI が実行できない、または実行すべきでない作業にだけ `[人]` を付ける。
- `[人]` の対象: インタビューとアンケートの実施、同意の取得、倫理審査、有料の論文・レポート・データベースの入手、社内データの取得とアクセス権の申請、専門家への確認、報告の公開の判断、秘密情報の入力。
- 人と AI が混ざる作業は 2 つのタスクに分ける。人が入手したものを AI が確かめる場合は、確かめる側を AI のタスクにし、人のタスクの直後に置く（上の T005 と T006）。
- 文字起こしの匿名化、入手した資料の抜き書き、インタビューガイドやアンケート票の下書きは AI のタスクにする。下書きの承認が要るなら、承認だけを `[人]` にする。
- `[人]` のタスクが収集の前に要るもの（同意書の準備、アクセス権の申請、有料資料の購入の判断）は、準備のフェーズに置き、早く着手できるようにする。

## 4. フェーズの構成

| フェーズ | 内容 | 主なタスク |
|---|---|---|
| Phase 1 準備 | 収集を始める前に要るもの | 出典 ID の範囲を取る、検索ログ `search-log.md` を作る、`evidence/`・`analysis/` を作る、インタビューガイド・アンケート票・同意書の下書き、`[人]` の入手・申請・審査 |
| Phase 2 収集 | Q8（`researchkit-collect`） | `plan.md` の情報源ごとの検索と取得、出典の実在の確認と等級づけ、抜き書き、データの取得と目録への記載、**反対の証拠を探す検索**、検索ログへの記録（見つからなかったことも） |
| Phase 3 分析 | Q9（`researchkit-analysis`） | 前処理、分析のスクリプトと `analysis/out/` の出力、抽出表、研究の質の評価、コーディングとテーマの抽出、図表、**反証条件の判定に使う指標の算出** |
| Phase 4 まとめ | Q10（`researchkit-findings`） | `findings.md` の主張の表、判定の基準ごとの答え、仮説ごとの反証条件の判定、残った問い、逆流（`hypotheses.md`・`issue-tree.md`・`docs/questions/` の更新）、`check.py` と `numbers.py` の確認 |

- タスクの順は、依存の順にする。データの取得は、それを使う分析の前に置く。人が入手するものに依存するタスクは、その `[人]` のタスクの後に置く。
- 各フェーズの冒頭に、そのフェーズの目的と、フェーズを終えたと言える条件を 1〜2 行で書く。
- `plan.md` の情報源・データ・分析・反証条件・反対の証拠の探し方の**すべての行**に、対応するタスクがあるようにする。`spec.md` の判定の基準 `AC` のすべてに、それを判定する分析とまとめのタスクがあるようにする。
- タスクの数の目安は、小さな RQ で 10〜20、大きな RQ で 30〜50 である。50 を大きく超えるなら、RQ を分けることを完了報告で勧める。
- レビュー（Q11・Q12）のタスクは書かない。工程の外で統括スキルが行う。

## 5. 手順

1. テンプレートを `RQ_DIR/tasks.md` に写す。すでにあれば、完了済み（`- [x]`）のタスクを消さずに更新する。
2. `plan.md` の各節から、§4 のフェーズにタスクを起こす。手法の参照文書にある作業の順序に従う。
3. §2 の書式と §3 の `[人]` の規則で書く。
4. 依存の節、並行の例、`[人]` のタスクの一覧を書く。
5. 次を点検する。
   - すべてのタスクが書式どおりか（チェックボックス、ID、パス、完了の確かめ方）
   - `plan.md` のすべての行と、`spec.md` のすべての `AC` に、対応するタスクがあるか
   - `[人]` が規則どおりか（AI ができる作業に付けていないか、人の作業に付け忘れていないか）
   - 依存の順が正しいか

## 6. 000 と 999 の扱い

| RQ | フェーズの読み替え |
|---|---|
| `000-research-foundation` | 主張を作らない基盤づくりである。準備: 共通の出典 `S000-` の範囲、`sources/` の書式の確認。収集（Q8）: 用語集 `docs/glossary.md`、データの目録 `data/manifest.md`、`data/raw/`・`data/large/` の置き場、共通の出典、検索ログの形式を整える。分析（Q9）: 試しのスクリプトを `commands.analysis` で実行し、`analysis/out/` に JSON が出ることを確かめる（`numbers.py` で 1 件突き合わせる）。まとめ（Q10）: 基盤の状態と残作業を `findings.md` に記録する（主張の表は作らない）。`[SQn]` は基盤の小問を指す |
| `999-research-report` | 準備: 全 RQ の状態の確認（すべて `完了` か `人の作業待ち`）、取り込む主張の一覧。収集の代わり（Q8、`researchkit-synthesize`）: `reports/report.md` の構成、決定ごとの結論、エグゼクティブサマリー、限界、次の問い。分析の代わり（Q9、`researchkit-publish`）: 読み手ごとの形式（`reports/publish/`）。不要なら「公開の形式は作らない」とその理由を記録するタスク 1 件にする。まとめ（Q10、`researchkit-findings` の統合モード）: 報告の結論と各 RQ の `findings.md` の整合の確認、逆流、`check.py` と `numbers.py` の確認。報告の公開の判断は `[人]` にする |

## 7. 完了報告

- `RQ_DIR/tasks.md` のパス
- タスクの総数と、フェーズ別・小問別の件数
- `[人]` のタスクの件数と内容（収集の前に要るものを先に）
- 並行できるタスクの例
- 点検の結果（`plan.md` の行と `AC` のカバレッジ、書式）
- 次の案内: `researchkit-analyze <RQ_NAME> --round 1`（Q7-1）
