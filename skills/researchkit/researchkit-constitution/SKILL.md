# researchkit-constitution スキル（R8: 調査の憲章）

調査の最上位の規範を作る。RQ の仕様、計画、収集、分析、主張、レビュー、統合報告は、すべてこの文書に従う。条項は、成果物を読んで**守れているかを判定できる形**で書く（「信頼できる出典を使う」ではなく「主張の根拠は等級 C 以上。結論に使う主張は等級 A を 1 件以上含む」）。

パスは `.researchkit/config.yaml` の `paths` で読み替える（以下は既定のパス。憲章は `paths.constitution`）。

## 0. 大原則

- **steering と矛盾させない。** 等級、確度、出典台帳、主張の書式、数値の参照の基本は steering（`.kiro/steering/research.md`）が定める。憲章は、その既定をこの調査に合わせて具体化し、必要なら変える（等級の定義、確度の段階の数と名前、付け方の規則）。steering の原則（出典のない事実を書かない、AI が挙げた文献を確かめる、`D` を根拠にしない、法的な判断をしない）は弱めない。
- **判定できる条項にする。** 各条項に MUST か SHOULD の印を付ける。MUST に反するものはレビューで CRITICAL、SHOULD に反するものは MEDIUM として扱う。
- **機械検証とそろえる。** `check.py` は `config.yaml` の `confidence.levels`、`sources.grades`、`sources.min_grade` を読む。憲章で確度の段階や等級を変えたら、`config.yaml` も同じにする（§4）。
- **根拠のない決まりは作らない。** 根拠にしてよいのは、`docs/concept/premises.md`（とくに RP1 読み手、RP7 要求する確度、RP9 倫理と個人情報、RP10 利害関係、RP11 言語）、`docs/method.md`、ユーザーの回答、既存の調査の決まりである。
- **書き出す前に合意を取る。** 自動モード（`--auto`）では §6 の規則で決めて記録する。
- ドキュメントは日本語で書く。

## 1. 引数と入出力

```text
$ARGUMENTS
```

引数は、追加の決まりや改訂の内容として扱う。`--auto` は位置を問わず取り除く。

| 入力 | 用途 |
|---|---|
| `docs/concept/seed.md`、`premises.md` | 読み手（RP1）、要求する確度（RP7）、倫理と個人情報（RP9）、利害関係（RP10）、言語（RP11） |
| `docs/method.md` | 採用した手法（定性調査や文献レビューの有無で、等級と確度の規則が変わる） |
| `.researchkit/config.yaml` | 現在の `confidence.levels`、`sources.grades`、`sources.min_grade` |
| 既存の調査の決まり（取り込みのとき） | 社内の調査ガイドライン、過去の報告書、引用や表記の規程 |

| 出力 | 様式 |
|---|---|
| `.researchkit/memory/constitution.md` | [templates/constitution.md](./templates/constitution.md) |
| `.researchkit/config.yaml` | `confidence.levels`、`sources.grades`（憲章で変えたときだけ） |

R8 として実行したときは、`researchkit-bootstrap` の記録の形で R8 を記録する（`docs(bootstrap): R8 憲章を作成`、trailer `Researchkit-Bootstrap: R8`）。単独で実行したときも記録する。改訂のときは、通常のコミット（`docs(constitution): 憲章を改訂（vX.Y.Z）`）にする。

## 2. モード判定

| 条件 | モード |
|---|---|
| `constitution.md` がなく、既存の調査の決まりもない | **新規** |
| `constitution.md` がなく、既存の調査の決まり（ガイドライン、過去の報告書の凡例）がある | **取り込み** |
| `constitution.md` がある | **改訂** |

## 3. 条項の構成

様式は [templates/constitution.md](./templates/constitution.md)。次の節を持つ。条項には ID（`K-1-1` の形）を振る。レビューの指摘で参照するためである。

| 節 | 中身 | 主な根拠 |
|---|---|---|
| 1. 出典の等級 | `A`〜`D` の定義と例、一次資料の扱い、孫引きの禁止、等級を下げる条件（ページを開けない、古い、利害がある）、プレプリントや自社発表の等級 | steering の「出典台帳」、`docs/method.md` |
| 2. 確度の段階と付け方 | 段階の名前と意味、根拠の数と等級からの付け方の表、確度を下げる条件（反証、独立でない根拠、推計の仮定）、統合報告での扱い。文献レビューを含む場合は GRADE との対応 | RP7 |
| 3. 引用の規則 | 原文のまま引く、出典 ID と頁・節、訳の明示と原文の保存、要約と引用の区別、引用の範囲（必要な範囲、本文が主、区別、出所の明示）、図表の転載 | — |
| 4. 数値の規則 | 単位、丸めの時点と桁、% とポイント、年度と暦年、為替の換算（レート、日付、方法）、物価の調整（指数と基準年）、推計は幅で示す、`{N:...}` の参照 | steering の「数値の参照」 |
| 5. 倫理と個人情報 | 同意、匿名化、個人情報をリポジトリに入れない、利用規約とスクレイピング、社外秘の扱い、法的な判断をしない | RP9 |
| 6. AI の利用の開示 | AI が関わった工程の記録と報告書での開示、AI の出力を出典にしない、人が確かめた範囲 | — |
| 7. 利害関係の開示 | 依頼主、資金、調査者の立場、利害のある主張の扱い | RP10 |
| 8. 文書の優先順位 | 食い違ったときに、どの文書を正とするか | — |
| 9. モードと人の判断 | 既定のモード、必ず人が判断すること（公開の判断など） | — |
| 10. 改訂の記録 | 版、日付、変更点 | — |

## 4. config.yaml との対応

| 憲章 | config.yaml | 合わせ方 |
|---|---|---|
| 2. 確度の段階 | `confidence.levels` | 強い順に同じ名前で並べる。`check.py` は、ここにない確度の値をエラーにする |
| 1. 出典の等級 | `sources.grades` | 強い順に並べる。最後の等級は「未確認（根拠に使えない）」にする |
| 主張の根拠に使える最低の等級 | `sources.min_grade` | 品質基準（R11 `researchkit-deliverable` の `docs/quality.md`）で決める。憲章では変えない |

- 段階や等級の名前を変えたら、既存の `findings.md` と `sources/` の値も直す必要がある（改訂の影響として示す）。
- `config.yaml` を直した後、`$CHECK --all` を実行し、新しいエラーがないかを確かめる（RQ がまだない段階では、エラーがないことだけを確かめる）。

## 5. 手順

### 新規

1. 入力を読み、[templates/constitution.md](./templates/constitution.md) の既定の条項を出発点に、条項の案を作る。既定は steering の等級と確度の定義に合わせてある。
2. 調査に合わせて具体化する。
   - 文献レビューを含む（`docs/method.md`）: プレプリントの等級、GRADE との対応を足す。
   - 定性調査を含む: インタビューの等級（一次資料だが、一般化には使えない）、定性調査だけを根拠にした主張の確度の上限を足す。
   - データ分析を含む: 再現できる分析の結果の確度、探索的な分析の扱いを足す。
   - 海外の数値を扱う（RP3）: 為替の換算の規則を具体化する。
   - 利害関係がある（RP10）: 利害のある情報源の等級と、開示の書き方を具体化する。
3. 影響の大きい論点を、推奨案つきで AskUserQuestion で聞く（1 ラウンド最大 4 問）。
   - 確度の段階の数と名前（既定の 4 段階のままでよいか）
   - 確度の付け方の厳しさ（「確実」に要る根拠の数と等級）
   - プレプリント、調査会社の推計、企業の自社発表の等級
   - AI の利用をどこまで報告書に開示するか
4. 案を示し、条項ごとに MUST／SHOULD の区別と内容を確かめる。
5. 確定したら `constitution.md` を書き、版を `1.0.0` にする。§4 のとおり `config.yaml` を合わせる。

### 取り込み

既存の調査の決まりを、ファイルを動かさずに移す。

1. 社内の調査ガイドライン、過去の報告書の凡例、引用や表記の規程から、決まりにあたる記述を集める。
2. 過去の報告書を数本読み、実際の書き方（出典の書き方、確度の言葉、数値の丸め、為替の扱い）を観察する。書かれた決まりと実態が違う点は、一覧にしてユーザーに確かめる。
3. steering の原則に反する決まり（出典のない数値を認める、など）は、そのまま移さず、違いと案を示す。
4. 確度の言葉が既存の報告書で使われている場合（例: 「高・中・低」）は、その名前を使ってよい。§4 のとおり `config.yaml` を合わせる。
5. 以降は新規の 4〜5 と同じ。

### 改訂

1. 変更点を示し、影響（どの `findings.md`、`sources/`、`docs/quality.md`、報告書が新しい条項に反するか、`config.yaml` のどの値が変わるか）を調べる。
2. ユーザーの了承を得てから改訂する。版を上げる（条項の追加・変更は minor、条項の削除・意味の変更は major、言い回しの修正は patch）。「改訂の記録」に日付と変更点を書く。
3. `config.yaml` を合わせ、`$CHECK --all` を実行する。新しいエラーが出た `findings.md` は、直すか、直す作業を報告する。
4. 自動モードでは改訂しない（§6）。

## 6. 自動モード（`--auto`）

| 論点 | 自動モードでの動作 |
|---|---|
| 新規の条項 | テンプレートの既定の条項を採り、§5 新規の 2 の具体化を入力から行う |
| 確度の段階、等級 | 既定（4 段階、`A`〜`D`）のまま。`config.yaml` は変えない |
| AI の利用の開示 | 開示する（既定の条項のまま） |
| 改訂 | しない。改訂が必要だと判断したら、提案として `auto-decisions.md`（調査全体の工程なら `docs/`、RQ の工程なら `studies/<NNN-name>/`）に記録し、見直しの優先度を「高」にして止まる |

- 自動で決めたことは `docs/auto-decisions.md` に記録する（`researchkit-bootstrap` の書き方）。確度の付け方と、プレプリント・推計の等級は、見直しの優先度を「中」以上にする。

## 7. 完了報告

- 版と、MUST の条項の要約（等級、確度の付け方、引用、数値、倫理、AI の開示、利害関係）
- `config.yaml` を変えたか（`confidence.levels`、`sources.grades`）
- 取り込みのとき: 書かれた決まりと実態の食い違い、steering と合わずに移さなかった決まり
- 改訂のとき: 影響を受ける成果物と、直す作業
- 次の案内: R9 `researchkit-questions`（`researchkit-bootstrap` の中で実行している場合は、その手順に戻る）

## 8. 禁止事項

- steering の原則を弱める条項を書くこと（`D` を根拠に使えるようにする、出典のない数値を認める、など）
- 判定できない条項（「適切に」「十分に」）を書くこと
- 確度の段階や等級を変えて、`config.yaml` を合わせないこと
- ユーザーの合意なしに書き出す、または改訂すること（自動モードの新規を除く）
- 法的な判断を条項にすること（著作権や個人情報の扱いで迷うものは `[人]` の確認にする条項にとどめる）
